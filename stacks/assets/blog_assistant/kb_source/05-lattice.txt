Section: The Private Walkways Between Specific Gates
Topic: The Centerpiece

Plain English explanation:

Most of an airport's traffic moves through the main concourse, but there is a smaller, more interesting system running underneath it: private walkways that connect specific gates directly to each other, skipping the general concourse entirely. A badge check happens at every single doorway along that walkway, every time, with no exceptions for someone who was already checked five minutes earlier.

What makes this system worth building at all is how smart it is about routing. Show one kind of boarding pass and you go to one gate. Show a different marker, a canary wristband for instance, and you get quietly routed to a gate the airport is testing, invisible to everyone but the operators running the test. Ninety percent of travelers go the normal way, ten percent get routed through the new gate, live, with real passengers, and nobody outside the airport notices anything happening.

The walkway system connects to three genuinely different kinds of destinations at once, a staffed counter, an automated kiosk, and an existing gate that was already running its own separate operation before this walkway system existed. All three get treated the same way by the walkway's own rules, which is exactly the point. It also opens its own separate door straight out to the regional airstrip mentioned earlier, a second and completely independent way to reach that same outside destination, distinct from the chartered flight route the network layer uses.

Technical explanation: The VPC Lattice Service Mesh

Everything in this stack hangs off a single CfnServiceNetwork named lattice-lab, provisioned with auth_type set to AWS_IAM so that every downstream invocation has to carry a signed request rather than relying on network location alone. The first service attached to it, CfnService lattice-lab-app, fronts the three tier app's compute through an INSTANCE type target group called lattice-lab-instance-tg. That target group listens on port 8080 (the same APP_TIER_PORT constant the three tier stack uses), runs an HTTP health check against /api/health, and calls a target healthy after 2 consecutive successes and unhealthy after 3 consecutive failures. Because Fargate tasks cannot register as INSTANCE type Lattice targets, the target here is a dedicated EC2 instance (threetier.lattice_instance_target_host) that exists purely to keep this demo real instead of mocked. An HTTP listener on port 80 forwards to that target group at weight 100, and that forward block is the service's default rule. VPC Lattice has no separate default CfnRule resource, the default_action on the listener is the rule. A CfnServiceNetworkServiceAssociation attaches the service to the network, and a CfnServiceNetworkVpcAssociation attaches app_vpc to the network with a purpose built security group, LatticeVpcAssociationSg, guarding the association.

On top of that default rule sit three progressively more interesting routing rules, all attached to the same http_listener with ascending priority values so they evaluate in a defined order. Priority 10, named path-v1, matches any request whose path starts with the prefix /v1/ (case insensitive) and forwards it at weight 100 to a second target group, lattice-lab-ip-tg, which is an IP type target group pointed at the exact same backend instance but addressed by its private IP instead of its instance ID, a clean way to prove out the IP target type without spinning up new infrastructure. Priority 20, named header-canary, matches on the header x-canary with an exact value of true and forwards to lattice-lab-lambda-tg, a LAMBDA type target group backed by a Python 3.13 inline function (CanaryLambda) that returns a small JSON payload announcing itself as the Lambda target group. Priority 30, named weighted-canary, matches the /canary/ prefix and splits traffic 90/10 across two target groups in a single WeightedTargetGroupProperty list, sending 90 percent to the original instance target group and 10 percent to lattice-lab-alb-tg, an ALB type target group that points straight at the three tier stack's application load balancer ARN. Between the path match, the header match, and the weighted split, this one listener demonstrates all three of Lattice's rule based routing patterns off a shared backend footprint.

L4c layers HTTPS and TLS passthrough onto the same service network. Since there is no real domain in this lab to validate a public ACM certificate against, and ACM Private CA runs roughly 400 dollars a month just to exist, the stack generates its own self-signed certificate with openssl at synth time (RSA 2048, 3650 day validity, CN of lattice-lab.internal.example) and imports it into ACM through an AwsCustomResource calling ACM's importCertificate API directly, since ImportCertificate has no native CloudFormation resource type. The certificate's SAN list covers both lattice-lab.internal.example and tls.lattice-lab.internal.example so the one cert can satisfy both services Lattice validates against. certificate_arn and custom_domain_name are set as direct L1 property assignments on the CfnService object rather than constructor arguments, because in the Lattice CFN model those fields belong to the service, not the listener. An HttpsListener on port 443 forwards to the same instance target group used by the HTTP listener. A second service, TlsPassthroughService (lattice-lab-tls), carries its own custom domain (tls.lattice-lab.internal.example is required because Lattice rejects a TLS_PASSTHROUGH listener on a service without a custom domain, and reusing the main service's domain across two services would collide) and its own TLS_PASSTHROUGH listener on port 443, forwarding raw encrypted bytes to lattice-lab-tls-tg, an INSTANCE type target group on port 443 over TCP with health checks disabled, since Lattice never terminates TLS here and cannot health check through it. This path is structurally complete but not yet end to end verified, since the app tier instance only listens on plain HTTP 8080 today and has no TLS listener of its own to receive the passed through traffic.

L4d is the zero trust layer sitting underneath all of that routing. A CfnAuthPolicy is attached to the service network's ARN and a second, identically shaped one to the service's ARN, both statements allowing vpc-lattice-svcs:Invoke from any principal but gated by a condition requiring aws:SourceVpc to equal app_vpc's VPC ID, so IAM identity alone is not enough, the request also has to originate from the expected VPC. As defense in depth alongside that policy, the stack looks up the AWS managed prefix list for VPC Lattice itself (com.amazonaws.<region>.vpc-lattice, resolved through an AwsCustomResource call to describeManagedPrefixLists) and adds an ingress rule to LatticeVpcAssociationSg that only allows traffic from that prefix list, on all ports, into the VPC association's security group.

L4e is the hybrid path, and it is where the stack reaches outside AWS entirely. CfnResourceGateway OnpremResourceGateway sits in app_vpc's private subnets behind ResourceGatewaySg, and it exists to reach an on-premises broker over TGW and VPN. CfnResourceConfiguration OnpremBrokerResourceConfig is a SINGLE type, TCP protocol resource configuration scoped to port 9092 (a Kafka style broker port) with its resource_configuration_definition pointing at network.broker's private IP address, and a CfnServiceNetworkResourceAssociation wires that resource configuration into the same lattice-lab service network everything else lives on, so on-prem resources become addressable through Lattice right alongside the AWS native services. The stack also stands up a second, independent access pattern in provider_vpc: an ec2.CfnVPCEndpoint of type ServiceNetwork, pointed at the service network's ARN, guarded by ServiceNetworkEndpointSg whose only ingress rule permits traffic from provider_vpc's own CIDR block. Because provider_vpc is deliberately never given a full CfnServiceNetworkVpcAssociation, this PrivateLink powered endpoint is the demonstration of the lighter weight alternative, a VPC that wants to reach the network's services without formally joining it.

The observability and administrative layer, L4f, closes the stack out. ServiceNetworkAccessLogs is a CloudWatch Logs group with one week retention, encrypted with security.logs_key, and ServiceAccessLogsBucket is a versioned, KMS encrypted S3 bucket (using security.buckets_key with bucket key enabled), fully blocking public access, enforcing SSL, and shipping its own server access logs to security.s3_access_logs_bucket under the prefix lattice-access-logs-bucket/. The bucket's resource policy grants vpc-lattice.amazonaws.com PutObject scoped by an aws:SourceAccount condition, and separately the KMS key grants encrypt and decrypt to that same service principal, since SSE-KMS delivery needs both the S3 side and the KMS side authorized independently. Two CfnAccessLogSubscription resources then wire the actual delivery: one on the service network's ARN delivering to the log group, one on the service's ARN delivering to the S3 bucket, so network level and service level access logs land in different destinations. A second, independently routable Lambda backed service, DualStackService (lattice-lab-dualstack), fans the network out further with its own target group, listener, and association, though the original intent of using it to demonstrate IPv6 dual stack via ip_address_type on the target group config turned out to be a dead end. VPC Lattice's API rejects that property outright for LAMBDA type target groups, since ip_address_type is only honored on IP type target groups, which would need real IPv6 enabled subnets this lab intentionally does not provision. Finally, an AWS RAM cross account share is wired in behind a config.ENABLE_RAM_SHARE flag, a CfnResourceShare named lattice-lab-service-network-share that shares the service network's ARN with config.SECOND_ACCOUNT_ID and sets allow_external_principals to False. When that flag is off, which is the default without a second account ID configured, the stack instead emits a CfnOutput spelling out exactly what the share would have created, so the cross account design is documented and reviewable even when it is not actually deployed.
