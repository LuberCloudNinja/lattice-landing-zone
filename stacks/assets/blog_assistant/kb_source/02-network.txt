Section: Four Runways, One Set of Rules
Topic: The Ground Beneath Everything

Plain English explanation:

An airport with four separate runway systems that each make up their own traffic rules is an airport waiting for a collision. This project builds four separate zones, one for the main application, one for a partner airline's counter, one dedicated entirely to inspection, and one standing in for a small regional airstrip connected by a private chartered route, and gives them one shared rulebook for how traffic moves between them.

The rule is simple to say and strict in practice. Every zone's default route, no matter what it is trying to reach, passes through the inspection zone first. Not by convention, not by a note in a handbook that someone might forget to follow, but because the routing tables themselves have no other path. A plane cannot decide to skip the checkpoint because there is no taxiway that goes around it.

Technical explanation: The Network Core

The network core is four VPCs stitched together through a Transit Gateway, and the shape of each VPC's subnet tiers exists specifically to keep two jobs from colliding on the same route table. app-vpc (10.1.0.0/16, per the routing comments in the file) gets three tiers: Public, which holds the NAT Gateway and the internet gateway, TgwAttach, a /28 tier that hosts the Transit Gateway attachment ENIs and defaults 0.0.0.0/0 to that NAT Gateway, and Private, a /24 compute tier that defaults 0.0.0.0/0 to the Transit Gateway instead. inspection-vpc (10.0.0.0/16) needs a fourth tier because it carries two kinds of traffic that must never share a default route: Public (with its own NAT instance, more on that below), TgwAttach (/28, default route to the GWLB endpoint, wired later in inspection_stack.py), GwlbEndpoint (/28, default route back to the Transit Gateway), and Firewall (/24, default route to the NAT instance for the firewall fleet's own management traffic). provider-vpc (10.2.0.0/16) is the plain case, just Public and Private /24 tiers, with the Private tier's default route pointed at the Transit Gateway. onprem-vpc is the odd one out: it never gets a Transit Gateway VPC attachment at all. Its Public subnet holds the libreswan Customer Gateway instance and its Private subnet holds the placeholder broker, and the Site-to-Site VPN is the only path in or out, which is deliberate, the whole point is to behave like a real hybrid network reaching AWS over a VPN or Direct Connect rather than taking a VPC peering shortcut. One more detail worth flagging: app_az_count is pinned to at least two AZs (max(az_count, 2)) regardless of the MULTI_AZ flag, a holdover from when RDS's DBSubnetGroup required two AZ coverage, and the comment notes it was left in place after the data tier moved to DynamoDB because subnets themselves cost nothing and removing it risked destabilizing stacks that already reference those exact subnet names.

The Transit Gateway itself (CfnTransitGateway, logical id Tgw, described in code as 'lattice-lab transit gateway') is built with default_route_table_association and default_route_table_propagation both set to disable, so nothing gets wired automatically, every association and every propagation in this stack is explicit. Two route tables do all the work: SpokeRouteTable (spoke_rt) and InspectionRouteTable (inspection_rt). AppVpcAttachment and ProviderVpcAttachment are both associated to spoke_rt and propagated into inspection_rt, and the VPN's auto-created attachment gets identical treatment later, associated to spoke_rt and propagated into inspection_rt. InspectionVpcAttachment, by contrast, is associated only to inspection_rt, and it carries options={'ApplianceModeSupport': 'enable'}, which the comment flags as mandatory once the GWLB target group on the other end also has appliance mode enabled, since both switches have to be on for flow symmetry. The routing logic is where the design intent shows up clearly. spoke_rt gets exactly one static route, 0.0.0.0/0 pointed at InspectionVpcAttachment, and nothing else, no propagated spoke CIDRs at all, which means app-vpc, provider-vpc, and the VPN cannot see each other's address space directly through this table. Every packet leaving a spoke, whether headed to the internet or to another spoke, lands in inspection-vpc first. inspection_rt is the mirror image: it collects the propagated routes from all three spoke attachments so return traffic can find its way home, plus two static routes added by hand. The first is 0.0.0.0/0 pointed at AppVpcAttachment, because app-vpc is the only spoke with a path to the internet, so this is what sends inspected north-south traffic back out through app-vpc's NAT Gateway once it clears the firewall. The second is the onprem CIDR pointed at the VPN's Transit Gateway attachment, added as a plain CfnTransitGatewayRoute because the VPN connection is created with static_routes_only=True, meaning there is no BGP session for that route to propagate from, so it has to be written explicitly or traffic to onprem would have nowhere to go once it reached inspection_rt.

app-vpc's internet egress is a single managed NAT Gateway (CfnNatGateway, logical id AppNatGateway, backed by an Elastic IP called AppNatEip) placed by hand in the first Public subnet rather than through the Vpc construct's own nat_gateways parameter (all four VPCs set nat_gateways=0), specifically so the stack can control which subnet the gateway lands in and reference its id when wiring the TgwAttach tier's default route. That is SPEC.md Section 4's rule of one NAT Gateway total, made literal in code. inspection-vpc breaks that rule on purpose, but with an EC2 instance instead of a second managed NAT Gateway. InspectionNatInstance sits in inspection-vpc's own Public subnet with source_dest_check disabled and a security group, InspectionNatSg, that only accepts traffic from the inspection-vpc CIDR itself, and its user data does the router setup by hand: sysctl net.ipv4.ip_forward=1, an iptables POSTROUTING MASQUERADE rule on whatever the default route's outbound interface turns out to be, and a small systemd unit, inspection-nat-rules.service, that restores those iptables rules from a saved file on every boot, since iptables rules do not otherwise survive a restart. The reason it cannot just ride app-vpc's shared NAT Gateway is worth spelling out in full. app-vpc's NAT sits behind an IGW ingress edge-association route table, built in inspection_stack.py, that redirects every packet returning to that NAT's Elastic IP through a GWLB endpoint for inspection. The firewall fleet's own outbound traffic, package updates and rule syncs, originates from inspection-vpc's own CIDR, which nftables classifies as untrust because it is neither the trust nor the dmz range, so that return traffic would loop back through the same GWLB redirect and hit the untrust to untrust path, which has no rule and defaults to deny. In effect, the firewall would be unable to update itself. A second, uninspected NAT keeps that recursion from ever happening, and using a plain EC2 instance instead of a second managed NAT Gateway keeps this narrow exception cheap relative to the project's one NAT Gateway cost intent.

The simulated on-premises link stands in for a Direct Connect circuit, and it runs entirely on a Site-to-Site VPN with a libreswan instance playing the customer gateway device. LibreswanCgw is a plain EC2 instance in onprem-vpc's Public subnet with source_dest_check disabled, which the comment is careful to call out as the legitimate use of that setting here, a classic NAT-instance and router pattern, unlike the GWLB-fronted firewalls elsewhere in the stack. Its security group, LibreswanSg, allows UDP 500 (IKE) and UDP 4500 (IKE NAT-T) from any IPv4 address, which looks wide open until you remember that AWS's VPN service endpoints do not have fixed source IPs, so a real customer gateway appliance would need the same rule. On the AWS side, OnpremCustomerGateway is a CfnCustomerGateway with bgp_asn 65000 and its ip_address pointed at the libreswan instance's Elastic IP (LibreswanEip), and OnpremVpnConnection is created with static_routes_only=True and two tunnel options carrying pre-shared keys from _generate_psk, which prefixes a random 48 character hex string with the letter k so the value never starts with a zero, satisfying AWS's PSK format rule. Because a VPN attached to a Transit Gateway does not expose its auto-created TGW attachment id through CloudFormation's ordinary GetAtt (and because AWS::EC2::VPNConnectionRoute only works against a Virtual Private Gateway, not this setup), the stack looks the attachment id up at deploy time with a scoped AwsCustomResource, VpnTgwAttachmentLookup, calling describeTransitGatewayAttachments filtered on the VPN connection's resource id. That attachment id is what gets associated into spoke_rt, propagated into inspection_rt, and pointed at by the static onprem route described above.

LibreswanEip attaches to the instance by instance_id, which means the instance has to exist before the EIP can attach, and that ordering means libreswan's own user data, baked in at instance create time, can never reference that EIP's eventual address without creating a circular CloudFormation dependency. So the boot script discovers everything for itself at runtime instead: it pulls its own public IP from the IMDSv2 metadata service, polls ec2:DescribeCustomerGateways for a gateway whose ip-address filter matches that IP, polls ec2:DescribeVpnConnections for the connection tied to that gateway, and then reads the two tunnels' OutsideIpAddress values out of VgwTelemetry, each stage retried up to ten times with a fifteen second sleep in between. From there it writes two libreswan connection files, aws-tunnel1.conf and aws-tunnel2.conf, both authby=secret and ikev2=no, with leftsubnet set to the onprem CIDR and rightsubnet 0.0.0.0/0, aes128-sha1 with modp1024 for both IKE and phase 2, an eight hour IKE lifetime, a one hour SA lifetime, and dead peer detection that restarts the tunnel after a thirty second timeout. The two pre-shared keys get written into /etc/ipsec.secrets and the file is chmod 600 before ipsec is enabled and restarted. Going the other direction, onprem-vpc's Private subnets, where the broker lives, get one summarized route back toward AWS: 10.0.0.0/14 pointed at the libreswan instance, which covers inspection-vpc (10.0.0.0/16), app-vpc (10.1.0.0/16), and provider-vpc (10.2.0.0/16) in a single line instead of three separate routes.

The placeholder Kafka broker is intentionally minimal. PlaceholderBroker is an EC2 instance in onprem-vpc's Private subnet, and its user data installs nmap-ncat and runs a systemd unit, broker-placeholder.service, executing ncat -k -l 9092 with Restart=always, brought up immediately with systemctl enable --now. Its security group, BrokerSg, allows TCP 9092 in from 10.0.0.0/8, wide enough to cover the three AWS side /16s, inspection, app, and provider, that reach it over the tunnel without needing to enumerate each one by name. The comment above it says exactly what it is for: it gets swapped for a real Kafka broker in kafka_stack.py later, and until then it exists to prove that the path from an AWS-side subnet, through the Transit Gateway, into inspection_rt, across the VPN, and into onprem-vpc actually works end to end. That is also why the stack exports BrokerPrivateIp and BrokerInstanceId, alongside TransitGatewayId, VpnConnectionId, LibreswanPublicIp, and LibreswanInstanceId, as CfnOutputs meant for an SSM session and a simple nc verification step.
