Section: The Arrivals Hall and the Real Operation Behind It
Topic: The Passenger Experience

Plain English explanation:

Anyone can walk into an arrivals hall. It is public by design, there is a departure board on the wall, and there is no reason to check anyone's identity just to let them read it. But the actual work of running an airline, baggage routing, crew scheduling, gate assignments, happens in a back office that the public never sees and never should.

This project draws that line carefully. The public hall is served straight from a private archive that nobody outside the airport can browse directly. For the handful of requests that need the real operation, there is exactly one hallway connecting the two, and that hallway only carries one kind of traffic. Nobody wanders in off the street and accidentally ends up in the back office.

There is a second, entirely separate arrangement worth knowing about. A different partner runs their own small operation elsewhere on the property, and this project's application needs to reach exactly one counter at that partner's office. Rather than merging the two properties together, which would mean either side could eventually wander into the other's territory, a single narrow connection gets built that only goes one direction. The partner's office has no path back into this project's territory at all, even if it wanted one.

Technical explanation: The Application Path

The three tier stack, defined in threetier_stack.py, is the classic web, app, and data separation, built so the web tier can never touch the database directly and only the app tier holds that permission. CloudFront sits in front of everything as the single public entry point, with two behaviors defined on the WebDistribution: a default behavior that serves static assets out of a private S3 bucket, and an /api/* behavior that forwards to the internal application load balancer. Nothing in the app tier is internet facing on its own. The ALB, AppAlb, is created with internet_facing=False and lives in the app VPC's Private subnets, so the only way to reach it is through CloudFront's VPC origin, not through any public listener someone could hit directly.

The web tier used to be a placeholder page, but it isn't anymore. app/frontend-next is a real Next.js and Tailwind application built with output: 'export' in its next.config.js, and the pipeline's Synth step runs that build before cdk synth ever executes, so by the time threetier_stack.py calls s3_deploy.Source.asset() against app/frontend-next/out, there are real static files sitting there to upload. The WebBucket itself stays locked down: versioned, KMS encrypted with security.buckets_key, block_public_access set to BLOCK_ALL, enforce_ssl on, and reachable only through an Origin Access Control on the S3BucketOrigin that CloudFront uses. Because Next.js's static export writes one directory per route (a post like blog/hybrid-cloud-airport-story ends up as blog/hybrid-cloud-airport-story/index.html), and a private, OAC backed bucket doesn't auto append index.html to subdirectory requests the way an S3 website endpoint would, the stack adds a small CloudFront Function, NextStaticUrlRewrite, running on the JS_2_0 runtime at the default behavior's viewer request event, which rewrites any URI ending in a slash, or containing no dot at all, to its index.html file right at the edge. That keeps the whole rewrite free tier eligible with no Lambda@Edge involved.

The /api/* behavior is where CloudFront's VPC origin feature does the real work: origins.VpcOrigin.with_application_load_balancer(self.alb, http_port=80) lets CloudFront reach directly into the VPC and hit the ALB's port 80 listener, with an origin request policy of ALL_VIEWER_EXCEPT_HOST_HEADER and caching disabled, so there is no need for a public facing load balancer at all. That listener, AppListener, forwards to AppTargetGroup on port 8080, target_type IP rather than INSTANCE, because Fargate's awsvpc networking mode has no host instance to register a target by id against. The target group's health check hits /api/health with a healthy_threshold_count of 2 and an unhealthy_threshold_count of 3. Behind that target group sits AppService, an ECS Fargate service on the smallest task size (256 CPU units, 512 MiB of memory) built from app/backend's Dockerfile through ecs.ContainerImage.from_asset(), running at a desired_count of 2 when MULTI_AZ is on and 1 otherwise, with enable_execute_command turned on for ECS Exec access and a deployment circuit breaker set to roll back automatically on failure.

The data tier is a single DynamoDB table named latticelab, with a plain string partition key called id, on demand billing, an AWS managed KMS key, and point in time recovery turned on. Access to it isn't gated by a security group at all, since DynamoDB has no listening port of its own to control; instead the stack calls grant_read_write_data() straight onto the app task's IAM role, which is the right control surface for a managed API endpoint like this one rather than a network level one. Getting Fargate tasks to even start inside the app VPC required its own set of VPC endpoints: ECR, ECR Docker, and CloudWatch Logs as interface endpoints, plus S3 and DynamoDB as gateway endpoints, after discovering the hard way that routing the ECR auth handshake out through the NAT gateway and the inspection path wasn't fast or reliable enough (the task failed with an i/o timeout dialing port 443 during registry auth). One more resource rounds out this stack: LatticeInstanceTargetHost, a small dedicated EC2 instance running the same backend code as a systemd service. It exists purely because VPC Lattice's INSTANCE type target groups need a real EC2 instance id to register against, something a Fargate task can never provide, so this one host preserves that demo path without putting the actual app tier workload back on EC2.

The PrivateLink pattern in privatelink_stack.py is a deliberately separate exercise from the three tier app, built to prove a one way connection between two VPCs that never peer. A minimal stdlib HTTP server runs on Fargate in the provider VPC, on ProviderCluster and ProviderTaskDefinition at the same 256 CPU, 512 MiB task size, listening on port 8080, behind an internal Network Load Balancer named ProviderNlb whose NetworkTargetGroup uses IP targets on TCP port 8080. That NLB gets wrapped in a CfnVPCEndpointService with acceptance_required set to False, which fits a single account lab rather than a real cross account offering that would need a manual accept step. On the consumer side, app_vpc creates an InterfaceVpcEndpoint called ProviderInterfaceEndpoint against that service's generated name, with private_dns_enabled left off since a friendly DNS name would need domain ownership verification that doesn't make sense for a lab; consumers resolve the provider through the endpoint's own generated DNS name instead, which the stack exposes as a CfnOutput.

What makes this one way rather than a peering relationship is that PrivateLink projects the provider's NLB into the consumer's VPC as an ENI, and nothing more. There is no VPC peering connection anywhere in this pair of stacks, no route table entry for the provider VPC's CIDR inside app-vpc, and no route table entry for app-vpc's CIDR inside the provider VPC. The consumer can reach the provider through that ENI, but the provider has no corresponding path back into the consumer's VPC at all. Because there is no routing between the two CIDR blocks, they could overlap completely without any conflict, even though in this project they happen not to, sitting at 10.1.0.0/16 and 10.2.0.0/16. The stack also has to account for availability zones on the consumer side: a VPC Endpoint Service only supports the AZs its backing NLB actually has nodes in, so the interface endpoint's subnet selection is restricted to just the AZs the provider's NLB is deployed in, rather than all of app-vpc's Private subnets, since the two VPCs' AZ counts are not forced to match each other.
