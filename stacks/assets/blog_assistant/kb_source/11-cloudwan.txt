Section: Joining an Airline Alliance
Topic: Growing Beyond One Property

Plain English explanation:

Say this airport wants to start codesharing flights with a sister airport in another city. Ripping out the existing taxiway system to do it would ground every flight already scheduled, so instead a new, purpose built alliance network gets stood up alongside the old one, and traffic migrates onto it a little at a time. The existing taxiway system stays running the whole time, registered with the new alliance network as a bridge rather than replaced outright.

It is worth saying plainly that one part of this migration did not go perfectly. A specific route into one segment of the new network could not be fully completed during this build, a genuine limitation on the provider's side rather than something this project got wrong. Rather than hide that, the gap is documented directly in the code where anyone reviewing it will actually see it. This whole alliance layer only turns on when explicitly requested, because a second city is not free to operate.

Technical explanation: Multi Region Cloud WAN

The backbone of this section is cloudwan_stack.py, which stands up an AWS Cloud WAN core network as policy-as-code rather than click-ops. The stack creates an nm.CfnGlobalNetwork construct named GlobalNetwork, then an nm.CfnCoreNetwork named CoreNetwork that hangs off it, and every routing decision the core network makes lives in a single Python dictionary called POLICY_DOCUMENT that gets passed straight into policy_document. That matters because Cloud WAN's entire behavior, which VPCs land in which segment, which segments can talk to which others, is expressed as versioned code sitting in the repo instead of state that only exists in the console. The core network id comes back out as an SSM parameter at /lattice-lab/cloudwan/core-network-id, which is how the cross-region stack finds it later without any manual copy-pasting of ARNs between accounts or regions.

POLICY_DOCUMENT defines four segments, and the names were chosen to mirror the customer's own vocabulary rather than generic AWS terms: FastTrack for production, SkyPath as the proxy segment, SkyTransit for hybrid and on-prem reachability, and Workload. Workload is the interesting one because it sets isolate-attachments to true, meaning nothing inside that segment can reach anything else inside that segment unless you explicitly grant it through a share action, which is the segment-isolation half of the demo. SkyTransit is the opposite case, it gets a segment-actions entry with action set to share, mode set to attachment-route, sharing itself into FastTrack, which is the controlled cross-segment reachability half. Attachments get sorted into these segments automatically through attachment-policies, four rules numbered 100, 110, 120, and 130, each matching on a tag-value condition against a key of segment and routing constant-association style into FastTrack, SkyPath, SkyTransit, or Workload respectively. In practice that means app_vpc gets tagged segment equals WORKLOAD and provider_vpc gets tagged segment equals FASTTRACK on their CfnVpcAttachment resources, and the policy engine does the rest, the stack itself never manually wires an attachment into a segment.

The cross-region piece lives in region2_stack.py, which only deploys when config.ENABLE_CLOUDWAN is on and stage.py has set env to us-east-2 with cross_region_references set to True. It builds one small VPC, Region2ProdVpc with vpc_name region2-prod-vpc, sized from config.REGION2_VPC_CIDRS under the region2_prod key, capped at a single AZ, zero NAT gateways, and PRIVATE_ISOLATED subnets only at a /24 mask. There is no internet gateway and no NAT anywhere in this VPC, the only way in is Session Manager over interface endpoints for SSM, SSM_MESSAGES, and EC2_MESSAGES, gated by a security group that only allows inbound HTTPS on port 443 from the VPC's own CIDR block. That is the same SSM-only, no-bastion pattern used everywhere else in the project, just replicated into a second region. The test instance itself runs on config.DEFAULT_INSTANCE_TYPE with the latest Amazon Linux 2023 AMI, an IAM role carrying AmazonSSMManagedInstanceCore, ssm_session_permissions turned on, and an 8 GB encrypted EBS root volume. Its CfnVpcAttachment, named Region2VpcAttachment, is tagged segment equals WORKLOAD and passed the core_network_id that was threaded in from the us-east-1 stack through that SSM parameter, so the attachment falls into the same isolated Workload segment as app_vpc back in the home region, purely through the tag-driven policy rather than any region-specific wiring.

One honest wrinkle shows up in that same file: security_stack.py's customer-managed KMS keys are regional to us-east-1, and KMS keys do not span regions without setting up an explicit multi-region key, which was out of scope for this lab. So the region2 EBS volume falls back to the AWS-managed default key instead of the project's usual CMK-everywhere pattern. That is called out directly in the module docstring as a deliberate, documented exception rather than something that slipped through review.

The core network's edge locations carry their own ASNs, us-east-1 at 64513 and config.SECOND_REGION at 64514, drawn from an asn-ranges block of 64513 to 64555. That starting number is not arbitrary. The project's existing Transit Gateway, built in network_stack.py, was left to take AWS's default AmazonSideAsn, which landed on 64512, the bottom of the standard 16-bit private ASN block AWS hands out automatically. The first pass at this policy reused that same 64512 range for the edge location's own ASN and it caused a real BGP ASN collision, confirmed live through direct networkmanager create-transit-gateway-peering calls against the actual TGW, which failed the same way whether the registration was freshly created or fully propagated, which ruled out timing as the cause. Each side of a TGW-to-Core-Network peering needs a distinct ASN the same way any BGP session does, so the fix was to start the core network's asn-ranges one number above the TGW's own ASN, at 64513, so the two can never collide again even if the TGW's default-assigned ASN ever shifts within its own range.

The registration and peering between that existing TGW and the new core network both work, and work reliably. CfnTransitGatewayRegistration (TgwRegistration) and CfnTransitGatewayPeering (TgwPeering) both reach AVAILABLE consistently, confirmed live. What does not work, and is documented as such rather than quietly left out, is the next step in a real TGW-to-Cloud-WAN migration: attaching one of the TGW's route tables to a segment so that routes actually exchange between the two. The CfnTransitGatewayRouteTableAttachment resource type consistently fails with an opaque Fail to create Resource error carrying HandlerErrorCode InvalidRequest and no further detail in the reason string. This was chased down across more than six attempts covering every plausible root cause: the ASN collision described above, which was real and got fixed, a live route table versus a dedicated one, tested both, identical failure even against a freshly created, verified-empty, unassociated table, registration and peering propagation timing, both confirmed AVAILABLE well before each attempt, and the peering's own underlying EC2 transit gateway attachment, confirmed available. None of those explain the failure, and the API itself gives nothing else to go on. So the honest state of this project is that the TGW is genuinely integrated with the core network at the registration and peering layer, but the route-table-level route-sharing half of a full TGW migration is not demonstrated here, and that gap is called out in the stack's own docstring rather than papered over.
