Section: The Assistant in the Tower Who Cannot Touch the Yoke
Topic: A Co-Pilot, Not a Pilot

Plain English explanation:

Put an assistant in the control tower who can see everything a human controller sees, every sensor, every camera feed, every log from the security operations center, and who can actually answer real questions about what is happening. Ask why a gate is backed up and it will go look and tell you. Ask it to draft a proposed fix and it will.

But it cannot move a single plane. When it has a genuine suggestion, it writes up a formal change request and puts it in a human supervisor's inbox, exactly the way a junior controller escalates an idea to their shift lead rather than acting on it directly. The assistant has broad read access to the whole airport and almost no write access to anything that matters, and the one narrow exception still ends with a human reviewing the request before anything changes.

Technical explanation: The Agentic AI Layer

The agentic AI layer lives in stacks/agentic_ai_stack.py and is gated behind config.ENABLE_AI, off by default, because Bedrock AgentCore plus S3 Vectors plus a Knowledge Base are all meaningfully billable even sitting idle. The stack stands up two agent personas, network-operator and connectivity-planner, each with its own IAM role, its own route on a shared HTTP API (api_name agentic-ai-api), and its own Bedrock AgentCore Runtime, all pointed at the same orchestrator Lambda code (orchestrator/handler.py, a Bedrock Converse tool-use loop) but scoped to a different tool set through a TOOL_FUNCTION_ARNS environment variable built per persona. network-operator gets every read-only tool. connectivity-planner gets everything network-operator has plus one additional tool. The separation is enforced in IAM, not in a system prompt: the loop that grants tool_fns[tool_name].grant_invoke(orch_role) only iterates over that persona's own allowed_tools list, so network-operator's Lambda execution role has no invoke permission on the write-capable tool at all, full stop.

Memory is deliberately three tiers instead of one DynamoDB table. Working memory is a DynamoDB TableV2 named agentic-ai-working-memory, partition key session_id, on-demand billing, encrypted with the project's customer-managed key (security.secrets_key), point-in-time recovery on, and a ttl attribute so idle sessions expire themselves instead of accumulating forever. Durable memory is a plain S3 bucket (DurableMemoryBucket), versioned, KMS encrypted with security.buckets_key, that holds an append-only JSONL transcript per session and is kept indefinitely, independent of DynamoDB's TTL, until someone runs cdk destroy. Semantic memory is the deep one: an S3 Vectors bucket named agentic-ai-semantic-memory backed by a CfnIndex called semantic-memory-index (float32 vectors, 1024 dimensions, cosine distance), fronted by a Bedrock Knowledge Base of the same name that embeds ingested content with amazon.titan-embed-text-v2:0. That's the tier the search_memory MCP tool actually queries at runtime, via bedrock-agent-runtime:Retrieve scoped to the Knowledge Base's own ARN. Getting the semantic tier live surfaced two real permission gaps worth naming: S3 Vectors' async indexing runs under its own service identity (indexing.s3vectors.amazonaws.com), which needed an explicit KMS encrypt/decrypt grant separate from any bucket-level grant, confirmed by a live CREATE_FAILED with an AccessDenied on asynchronous indexing until that grant was added; and the Knowledge Base's IAM role needed its policy attached as an explicit iam.Policy construct with an add_dependency, because role_arn alone doesn't imply CloudFormation waits for a separately-attached policy, which produced a real race (CREATE_FAILED, no identity-based policy allows s3vectors:QueryVectors) on the first two attempts.

Seven MCP tool Lambdas back the actual tool surface: query_kafka, search_memory, get_network_health, query_governance, cloudwan_topology, detect_anomalies, and propose_connectivity. Every one is PYTHON_3_13 on ARM_64, VPC-attached into the private subnets behind a shared security group (McpToolSg, outbound only), with its own least-privilege IAM role built by the same _tool_role helper. query_kafka calls vpc-lattice:GetResourceConfiguration and vpc-lattice:GetResourceGateway against the Lattice resource-gateway attrs; get_network_health calls elasticloadbalancing:DescribeTargetHealth and ec2:DescribeVpnConnections; query_governance calls securityhub:GetFindings and config:DescribeComplianceByConfigRule; cloudwan_topology (only deployed when the Cloud WAN layer is enabled) calls networkmanager:GetCoreNetwork and ListAttachments; detect_anomalies queries a DynamoDB table that only really exists once the SageMaker stack deploys, degrading cleanly to an empty env var otherwise. Each of these seven is registered twice: once as a direct lambda:InvokeFunction target the orchestrator Lambda calls straight from Python (cheaper than round-tripping through MCP from inside another Lambda), and once as a genuine Bedrock AgentCore CfnGatewayTarget on a CfnGateway named agentic-ai-mcp-gateway (protocol_type MCP, authorizer_type AWS_IAM), so any real external MCP client, the AgentCore console, a different agent framework, a human with an MCP inspector, can discover and call the same tool over the actual MCP protocol. Wiring the Gateway targets up exposed a third gotcha worth naming plainly: granting the gateway's execution role invoke permission at the IAM identity level (fn.grant_invoke(gateway_role)) was not sufficient on its own, every GatewayTarget failed to create with an error that the gateway execution role lacked permission to invoke the Lambda. What actually fixed it was adding a resource-based policy directly on each Lambda, an explicit lambda_.CfnPermission with the gateway role's ARN as principal, on top of the identity-based grant, matching what AWS's own docs show for Lambda-backed Gateway targets.

propose_connectivity is the one tool in the whole layer with any write capability, and its blast radius is intentionally tiny. Its IAM role is allowed exactly four CodeCommit actions, GetBranch, CreateBranch, CreateCommit, and CreatePullRequest, scoped to the single repository named in config.CODECOMMIT_REPO_NAME, and nothing else. It never touches a running resource. It drafts a connectivity change and opens a pull request against the base branch in config.CODECOMMIT_BRANCH for a human to review and merge, which is also why it gets a longer 60 second timeout where every other tool Lambda defaults to 30. Only connectivity-planner's persona list includes it (PLANNER_ONLY_TOOLS), so only that persona's orchestrator role ever receives grant_invoke on it. network-operator physically cannot reach it, at the IAM level, regardless of what an operator asks the model to do, which is the point of the whole exercise: nowhere in this stack does either persona's IAM policy grant a single infrastructure-mutating action against real network resources.

The Bedrock AgentCore primitives themselves show up as five distinct CloudFormation resource types, each used for what it's actually for rather than as decoration. CfnMemory (named agentic_ai_memory) is AgentCore's own native session-memory service, configured with a semantic_default strategy and a summary_default strategy, indexed on session_id and agent_role, a 30 day event expiry, and encrypted with the same secrets_key CMK as the working-memory table; it's explicitly complementary to, not a replacement for, the three custom tiers described above. CfnWorkloadIdentity (named agentic-ai-lab) backs the Gateway's workload identity. CfnRuntime is provisioned twice, once per persona (agentic_ai_network_operator and agentic_ai_connectivity_planner), against a stub S3 code asset (agent_runtime_stub/agent_runtime.py), protocol_configuration HTTP, network_configuration PUBLIC, because AgentCore Runtime's real invocation contract is an always-on HTTP server, a genuinely different shape than the Lambda handler contract the actual working demo uses. That's called out honestly in the module docstring as a stub provisioned to demonstrate the construct end to end, the same pattern the project already uses for its Kafka stack. The real working path a caller actually hits is the Cognito-protected one: an HttpApi named agentic-ai-api with an HttpJwtAuthorizer backed by a Cognito user pool (agentic-ai-api-users, self sign up disabled, minimum password length 12 with upper, lower, digit and symbol required) sitting in front of both /network-operator and /connectivity-planner routes, because an HTTP API's default execute-api domain is public internet by construction and there's no VPC Link path for a Lambda-proxy integration, so leaving those routes unauthenticated would have been the one clearly un-zero-trust decision in an otherwise IAM-scoped design.
