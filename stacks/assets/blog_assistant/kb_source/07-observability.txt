Section: The Control Room
Topic: One Wall, Every Terminal

Plain English explanation:

Somewhere in the airport there is a control room with a wall of screens, and every terminal, every checkpoint lane, every gate feeds a live signal into that same wall rather than keeping its own private monitor somewhere nobody looks at. When a new wing gets added to the airport, its status screen gets bolted onto the same wall instead of getting its own separate room built for it.

That sounds like a small detail, but it changes how the airport actually gets operated day to day. One person can glance at one wall and know whether the checkpoint lanes are backed up, whether the private walkways are healthy, whether the construction crew's last renovation went smoothly, all without walking the property.

Technical explanation: Observability and Supporting Stacks

ObservabilityStack builds a single CloudWatch dashboard named lattice-lab (the CfnDashboard construct id is just Dashboard, dashboard_name is the string lattice-lab), and everything downstream treats that dashboard as a shared mutable object rather than a sealed artifact. The stack opens with a TextWidget reading lattice-lab -- interview demo health check at full 24-column width, then appends section after section as it wires in the other stacks it depends on: NetworkStack, InspectionStack, PrivateLinkStack, ThreeTierStack, LatticeStack, GovernanceStack, DriftRemediationStack, and SecurityStack are all passed in as keyword arguments and read directly for their metrics and ARNs. The interesting design choice is that self.dashboard is exposed as a plain CDK construct reference, not something scoped only to this file's own code, so optional layers that deploy later (Cloud WAN, Agentic AI, SageMaker, auto-heal) reach back into this same dashboard object and call add_widgets on it from their own stack files, auto_heal_stack.py being the concrete example already doing this. That ordering matters enough that the module docstring calls it out explicitly: ObservabilityStack now has to deploy after GovernanceStack and DriftRemediationStack in stage.py, a reversal from the original build, because its dashboard graphs governance_stack.py's custom metrics and drift_remediation_stack.py's Lambda directly and those resources need to exist first.

Before any widgets get added, the stack creates two CloudWatch log groups scoped to the inspection fleet only, SuricataEveLogGroup at /inspection-vpc/suricata-eve and NftablesPlLogGroup at /inspection-vpc/nft-pl, both with one week retention (logs.RetentionDays.ONE_WEEK), both encrypted with security.logs_key, and both set to RemovalPolicy.DESTROY so a lab teardown actually removes them. The module docstring is candid about a known gap here: these two groups exist with the right names and retention to match docs/inspection-architecture-reference.md section 5.3, but inspection_stack.py's launch template user data does not yet install or configure the CloudWatch Agent to actually ship /var/log/... into them, so they currently exist and cost nothing while sitting empty, and nothing populates them until that agent configuration lands as a follow up. Lattice's own service network and service access log destinations are deliberately not duplicated in this stack either, since those already live in lattice_stack.py as a CloudWatch Logs group plus an S3 bucket, created there because that stack needed them immediately to wire a CfnAccessLogSubscription.

The dashboard body itself is organized into labeled sections built from cw.GraphWidget and cw.LogQueryWidget instances. The first block, carried over from the original build, graphs GWLB firewall fleet health (HealthyHostCount and UnHealthyHostCount on the AWS/GatewayELB namespace) next to Lattice service traffic (TotalRequestCount and HTTPCode_5XX_Count on AWS/VpcLattice, keyed to the Service dimension value lattice-lab-app, the service's configured Name rather than a generated id or ARN), followed by an app tier ALB widget pulling threetier.alb.metrics.request_count() and the app target group's healthy host count and target response time, and a DynamoDB widget graphing consumed read and write capacity units against throttled requests. Both the GWLB and the later NLB widgets rely on a small helper, _elbv2_dimension_value, which pulls the sixth colon-separated field out of an ELBv2 ARN using cdk.Fn.select(5, cdk.Fn.split(':', arn)), a single extraction confirmed to work identically across AWS/GatewayELB, AWS/NetworkELB, and AWS/ApplicationELB dimension formats. A Network section follows with its own text header widget, graphing Site-to-Site VPN tunnel state (AWS/VPN TunnelState keyed to network.vpn_connection's VpnId, labeled 0=DOWN, 1=UP), Transit Gateway BytesIn and BytesOut against PacketDropCountBlackhole and PacketDropCountNoRoute, and the managed App NAT Gateway's BytesOutToDestination against PacketsDropCount and ErrorPortAllocation on AWS/NATGateway. A separate widget then graphs the self-managed inspection NAT instance using AWS/EC2 CPUUtilization and StatusCheckFailed instead, since that path runs as a plain EC2 instance and never gets AWS/NATGateway metrics the way the managed gateway does, a distinction the code comments call out directly. A PrivateLink section graphs the provider NLB's healthy and unhealthy host counts alongside ActiveFlowCount and NewFlowCount on AWS/NetworkELB.

Governance and Drift Remediation get their own sections toward the bottom of the dashboard. Because Config, Security Hub, and GuardDuty have no native findings-over-time metric, the Governance widgets read from a custom namespace, LatticeLab/Governance, graphing NonCompliantConfigRules, ActiveFindingsCritical, ActiveFindingsHigh, ActiveFindingsMedium, ActiveFindingsLow, and GuardDutyFindingsTotal, each on a 15 minute period with a Maximum statistic, populated by governance_stack.py's own metrics publisher Lambda. Next to that sits a LogQueryWidget running a CloudWatch Logs Insights query against governance.trail_log_group (fields @timestamp, eventName, then stats count(*) as events by bin(5m)) because CloudTrail itself doesn't expose a native metric for management event volume. The Drift Remediation section graphs drift_remediation.remediator_fn's invocation and error counts side by side with the governance-alerts SNS topic's number of messages published. Three layers are deliberately left off the whole dashboard, and the docstring says so plainly: KafkaStack is still a SPEC.md TODO skeleton with nothing running to graph, DiagramStack is a static CloudFront and S3 site with no runtime metrics worth a widget, and Region2Stack is an SSM only test instance whose existence is already covered by CloudFormation's own stack status.

ResourceGroupsStack is a much smaller, purely tag-based construct. It builds one umbrella CfnGroup named lattice-lab-all using resource_query type TAG_FILTERS_1_0 against resource_type_filters AWS::AllSupported and a single tag filter on Project equal to config.PROJECT_TAG, then loops over config.ALL_LAYERS to build one additional group per layer, each named lattice-lab-{layer}, each construct id the capitalized layer name suffixed with LayerGroup, and each filtered on both the Project tag and a Layer tag matching that specific layer value. Every group gets a CfnOutput exposing its name, UmbrellaGroupName for the umbrella group and a per-layer output named after the capitalized layer. The stack is intentionally left untagged with its own Layer value, on the reasoning stated directly in the code, that a tag-based query group which is itself part of the tag set it queries would be confusing to reason about, and there's nothing else in this stack that would benefit from being grouped that way anyway.

DiagramStack hosts the architecture reference site that this whole diagram-site directory produces, and it leans entirely on a private origin pattern rather than public website hosting. The S3 bucket, construct id DiagramBucket, blocks all public access, is versioned, encrypted with KMS via security.buckets_key with bucket_key_enabled turned on, enforces SSL, and ships its server access logs to security.s3_access_logs_bucket under the prefix diagram-bucket/, with removal_policy DESTROY and auto_delete_objects true so a lab teardown actually empties it. Static website hosting mode is deliberately left off, since that mode serves over plain HTTP and doesn't support Origin Access Control at all. In front of the bucket sits a CloudFront Distribution, construct id DiagramDistribution, using origins.S3BucketOrigin.with_origin_access_control (the modern OAC pattern rather than a legacy OAI), default_root_object index.html, minimum_protocol_version TLS_V1_2_2021, viewer_protocol_policy REDIRECT_TO_HTTPS, and allowed_methods restricted to ALLOW_GET_HEAD. A ResponseHeadersPolicy named lattice-lab-diagram-{region} attaches a content security policy of default-src 'none'; style-src 'unsafe-inline'; script-src 'none'; img-src 'self' data:; base-uri 'none', a policy that's actually enforceable because the generated page carries zero script tags and makes no external requests of any kind, alongside nosniff content type options, DENY frame options, a strict-origin-when-cross-origin referrer policy, and HSTS with a 365 day max age and include_subdomains enabled. A BucketDeployment named DiagramDeployment uploads the diagram-site directory (excluding generate_diagram.py, the script that produces the page's computed, grid-snapped SVG coordinates), invalidates /index.html on the distribution after each deploy, and sets cache-control to public, max-age=300, must-revalidate, so the short TTL plus the explicit invalidation is what actually forces freshness rather than any cache-busting file naming scheme. There's no custom domain and no WAF or signed URL restriction, so the output DiagramUrl resolves to the plain distribution.distribution_domain_name under *.cloudfront.net, a decision the module docstring says should be confirmed with the user before either gets added. The stack closes with eight cdk-nag suppressions, each with its own written reason: IAM4, IAM5, and L1 cover the framework-managed policies and Lambda that CDK's own BucketDeployment construct generates, S1 explains that a second bucket purely for access logging one static HTML page isn't worth the added infrastructure, CFR1 and CFR2 note that geo restriction and WAF are genuinely optional for an interview lab demo page, CFR3 makes the same access-logging tradeoff for CloudFront itself, and CFR4 notes that the distribution already sets TLS_V1_2_2021 in code and uses the default *.cloudfront.net certificate, which AWS enforces at TLS 1.2 or higher regardless, a case cdk-nag's check doesn't appear to recognize.
