Section: The Construction Crew That Checks Its Own Permits First
Topic: The Deployment Script

Plain English explanation:

How does an airport get built and changed at all, without accidentally closing a live runway in the process? There is a construction crew whose blueprints live in a locked, version controlled records office, not a public bulletin board anyone can scribble on. Before that crew touches a single runway, they run through a fixed checklist: turn the blueprint into an actual build plan, and, this is the part most people miss, check whether their own permit approval process has changed since last time, and update that process first if it has.

Only after that does the crew stop and wait for the airport director's physical signature. No signature, no groundbreaking, no matter how confident the crew is that the change is safe. That signature requirement exists specifically for anything with a real cost attached, and it never gets skipped.

Technical explanation: The Deployment Pipeline

The real, git driven deploy path runs through a single PipelineStack, and the first thing worth explaining about it is where the source lives. It reads from AWS CodeCommit, not GitHub, and the reason is written directly into the module docstring rather than left for someone to guess at later. The original plan was GitHub through CodeConnections, but that requires a GitHub App to be separately installed on the target repo, which is a different step from just OAuth authorizing the connection. Miss that install step and the Source stage fails with an error like "No Branch [main] found," even though the connection itself shows AVAILABLE in the console, which makes it a genuinely easy trap to fall into and a frustrating one to debug from the CodePipeline side. CodeCommit sidesteps the whole handshake: the stack does a codecommit.Repository.from_repository_name lookup against config.CODECOMMIT_REPO_NAME, wraps it in pipelines.CodePipelineSource.code_commit against config.CODECOMMIT_BRANCH, and authenticates with plain IAM credentials. The CodeCommit repo itself is not created by this stack at all, it is provisioned out of band through the AWS CLI or console, which keeps the stack focused on the pipeline rather than repo bootstrapping. The pipeline construct itself is a pipelines.CodePipeline named "Pipeline" inside PipelineStack, given the friendly name "lattice-landing-zone," with self_mutation=True, so a push that changes pipeline_stack.py itself causes the pipeline to redeploy its own definition before it ever gets to deploying application stacks.

The Synth step is a pipelines.ShellStep named "Synth" and it does more than run cdk synth. The install_commands first run pyenv global 3.12.13, because the standard CodeBuild image manages multiple Python versions through pyenv and 3.12.13 is installed but not selected globally by default, so without that line python3.12 simply is not on PATH. From there it builds a virtual environment with python3.12 -m venv .venv, activates it, and installs from requirements.txt. The commands block is where the newer addition lives: before cdk synth ever runs, the build step cds into app/frontend-next and runs npm ci followed by npm run build, then returns to the repo root. This exists because ThreeTierStack's web tier deploys the static export output of that Next.js app (built with Next's output: 'export' setting), and CDK's Source.asset() call needs real files on disk at synth time, not a promise that they will exist later. Node and npm are already present on the standard CodeBuild image since CDK itself depends on them, so no extra install step was needed to make that work. Only after the frontend build finishes does the step run npx cdk synth. The synth step also carries an env block setting ENABLE_CLOUDWAN, ENABLE_AI, and ENABLE_SAGEMAKER all to "true," and that block is flagged in a comment as deliberately temporary: Cloud WAN's core network and attachments, the Bedrock AgentCore and S3 Vectors and Knowledge Base pieces, and the SageMaker Async Inference endpoint all cost real money layered on top of what the rest of the project already runs, and the comment is explicit that these should be reverted to unset or explicitly "false" once a given demo is done, before the next pipeline run picks them back up.

Nothing in LandingZoneStage actually deploys without a human saying so first. pipeline.add_stage is called with pre=[pipelines.ManualApprovalStep("PromoteToLandingZone")], so the stage sits behind an approval action in the CodePipeline console and a reviewer has to click approve before CloudFormation touches a single resource in the stage. There is a smaller but equally deliberate piece of plumbing right after that: pipeline.build_pipeline() is called explicitly, which forces the underlying CodeBuild synth project and its IAM role to materialize immediately rather than being resolved lazily during CDK's own synth pass, and it has to run after add_stage or the LandingZone stage and its approval step would be locked out of a pipeline structure that had already been finalized. Once the project exists, the stack grants its role an iam.PolicyStatement allowing ec2:DescribeAvailabilityZones against all resources. That grant exists because cdk.context.json is deliberately not committed to the repo, since it is an account specific build artifact that has no business sitting in a public repo. Without a cached context file, every synth, including this one running fresh inside CodeBuild with no local cache, has to resolve each ec2.Vpc construct's availability zones through a live describe call instead of a cached lookup, and the read only, account wide grant is treated as a smaller and more honest footprint than checking in a file that goes stale and is tied to one AWS account anyway.

Once approved, the stage deploys in an order that is not arbitrary. SecurityStack goes first, full stop, because every other stack in the stage takes its CMKs and its permissions boundary in as constructor props rather than looking them up again later, which stage.py's own docstring calls out directly as "not by re-lookup." NetworkStack comes next, standing up the VPCs and Transit Gateway that later stacks build against. InspectionStack, PrivateLinkStack, and ThreeTierStack all follow, each one taking network and security as constructor props so they can build their GWLB endpoints, VPC endpoints, and application resources against the VPCs that already exist rather than trying to discover them. ThreeTierStack carries an explicit threetier.add_dependency(privatelink) that is not a functional dependency at all, it is there to fix a race. Both stacks add a small EC2 instance, LatticeInstanceTargetHost from the Lattice side and ProviderInstance from any future EC2 rollback path, and both draw against the same account level vCPU quota. Deploying them in the same parallel wave meant that whichever stack was mid replacement, freeing up vCPU as it went, had not always finished before the other one tried to claim that same capacity, so CloudFormation would fail with "requested more vCPU capacity than your current vCPU limit" even though the headroom genuinely existed a few seconds later. Forcing PrivateLinkStack to finish first removes that race outright rather than leaning on retry timing to paper over it. LatticeStack comes after, taking network, threetier, and security as props, followed by ResourceGroupsStack and DiagramStack.

The rest of the order follows the same logic of letting real dependencies dictate sequencing rather than guessing. GovernanceStack and DriftRemediationStack deploy next, unconditionally, since CloudTrail, Config, SecurityHub, and GuardDuty at this scale cost cents rather than the dollars that gate the optional layers further down. ObservabilityStack now deploys after both of those, a change from an earlier layout where it sat right after LatticeStack, because its dashboard graphs governance_stack.py's custom metrics and drift_remediation_stack.py's Lambda directly, and a dashboard cannot graph a metric that does not exist yet. BlogAnalyticsStack comes after that, waiting on both ThreeTierStack, since it adds a new CloudFront behavior onto ThreeTierStack's existing distribution, and ObservabilityStack, since it adds widgets onto that stack's existing dashboard. KafkaStack is conditional on config.ENABLE_KAFKA. The Cloud WAN pair is more involved: CloudWanStack deploys with cross_region_references=True and its own explicit environment in config.AWS_REGION, and Region2Stack deploys separately into config.SECOND_REGION (us east 2), consuming cloudwan.core_network.attr_core_network_id across that region boundary, which is exactly what cross_region_references exists to allow. SageMakerStack is gated behind config.ENABLE_SAGEMAKER. AgenticAiStack deploys last among the optional layers, after network hardening, governance, Cloud WAN, and SageMaker, because its MCP tools read state from all of them, and it only wires in the cloudwan_topology and detect_anomalies tools when the cloudwan and sagemaker objects it was handed are not None. AutoHealStack closes the whole stage out, deployed unconditionally and last, specifically because it sits downstream of every optional layer that may or may not exist by the time it runs.

One last wrinkle worth naming is how app.py and stage.py relate to each other, since it explains why the pipeline and local iteration do not collide. app.py instantiates LandingZoneStage twice, once directly as "LandingZone-Dev" for fast local work with cdk deploy --all, and once implicitly inside PipelineStack, which builds its own separate LandingZoneStage named plainly "LandingZone." That duplication is not an accident or leftover code, it is required, because a CDK Stage can only be parented once, so the pipeline cannot reuse the Dev instance even if it wanted to. cdk-nag's AwsSolutionsChecks is applied only to the Dev stage for the same reason cited in app.py's own comment, checking the pipeline's internal CodeBuild and CodePipeline plumbing, or its nested copy of an identical stage, would just double the findings to review without adding real coverage. It is a small detail, but it is the kind of detail that tells you the pipeline was built by someone who had actually hit the Stage-can-only-be-parented-once error once already.
