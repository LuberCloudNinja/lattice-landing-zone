Section: The Badge That Opens Every Door
Topic: Foundation, Deployed First

Plain English explanation:

Before an airport can open a single gate, it needs a badge system. Every employee, every contractor, every vendor truck driver needs one credential that says exactly what doors they can open, and just as importantly, what doors they cannot. If that badge system is weak, nothing else in the airport matters, because a bad badge can walk anywhere.

This project starts with exactly that. Before the runways, before the terminals, before anything else gets built, the badge system goes in first. Five separate keys get cut, one for the maintenance logs, one for the storage lockers, one for the vehicle fleet, one for anything sensitive, one for the alert system, so that losing one key never means losing all of them. Then a single master policy is written that says, no matter what any individual badge claims to allow, no badge may ever open the badge office itself, create new badges, or grant itself more access. That policy is not a suggestion. It is checked at every single door, every time, and it wins even if someone tries to argue their way past it.

Every other part of the airport that gets built after this point, the terminals, the checkpoint, the tower, takes this badge system as a given rather than inventing its own. That is not an accident. It is the first and most important decision in the whole build.

Technical explanation: The Security Foundation

SecurityStack is the first thing that synthesizes in this project, and everything else waits on it. That ordering is not incidental. Every downstream stack, network_stack.py, inspection_stack.py, threetier_stack.py, privatelink_stack.py, takes SecurityStack's keys and permissions boundary in as constructor props rather than resolving them at deploy time through an SSM parameter lookup or a CloudFormation export. That distinction matters more than it looks like on paper. A prop is resolved when the CDK app is built, so the dependency graph is explicit and visible in code, and cdk synth fails loudly if something is missing rather than deploying successfully and then failing later at runtime because a cross-stack lookup came back empty. I built SecurityStack as the single source of truth for identity and encryption for exactly that reason. I wanted every other stack's IAM role and every other stack's bucket or log group encryption to trace back to one place I could reason about, instead of five stacks each quietly assuming a key or a boundary existed somewhere in the account.

The stack provisions five separate customer managed KMS keys instead of one shared key, and that was a deliberate choice about blast radius, not an oversight. Each key comes out of a shared _make_key helper and is single purpose: LogsKey, aliased alias/lattice-lab-logs, for CloudWatch Logs encryption across the CloudTrail log group in governance_stack.py, the Suricata and nftables groups in observability_stack.py, and the Lambda log group in drift_remediation_stack.py. BucketsKey, alias/lattice-lab-buckets, for SSE-KMS on every S3 bucket in the project, including web, policy, access-logs, diagram, CloudTrail, and Config. EbsKey, alias/lattice-lab-ebs, for root volume encryption on every EC2 instance and launch template. SecretsKey, alias/lattice-lab-secrets, which is provisioned and exported as a prop even though nothing in the project currently stores a secret in it, since the RDS secret went away when threetier_stack.py moved to DynamoDB, kept around for whatever future stack needs one. And SnsKey, alias/lattice-lab-sns, for the governance-alerts topic in drift_remediation_stack.py. Every key has enable_key_rotation set to True, and every key's resource policy grants only two things: the account root, which is AWS's own recommended default so ordinary IAM policies and grants keep working, and the one AWS service principal that actually needs it, logs.amazonaws.com, s3.amazonaws.com, ec2.amazonaws.com, secretsmanager.amazonaws.com, or sns.amazonaws.com. The EC2 key policy goes one step further and adds a Bool condition, kms:GrantIsForAWSResource set to true, so the grant only fires for genuine AWS-managed EBS encryption rather than an arbitrary caller claiming to be EC2. Splitting the keys this way means a compromised grant on SnsKey has no path to SecretsKey. It costs almost nothing in operational overhead and it buys real containment.

Sitting next to the CMKs is S3AccessLogsBucket, the one shared destination that every other bucket in the project, web, policy, lattice access logs, diagram, plus governance_stack.py's CloudTrail and Config buckets, points its own server_access_logs_bucket property at. It is deliberately encrypted with S3_MANAGED (SSE-S3) rather than the BucketsKey CMK, because it is receiving deliveries from the S3 Log Delivery Group, and CDK's bucket-policy-based log delivery path is the well-trodden one with SSE-S3; wiring SSE-KMS in here would only add key-policy and grant surface for a bucket that never holds anything more sensitive than access-pattern metadata. The bucket is still versioned, still BLOCK_ALL on public access, still enforce_ssl, and still set to RemovalPolicy.DESTROY with auto_delete_objects for the lab context. The one thing it does not have is its own server_access_logs_bucket, because a bucket cannot log to itself, and that gap is the single deliberate exception to the project's otherwise universal rule that every bucket gets access logging. I documented that exception directly against the cdk-nag AwsSolutions-S1 suppression on this bucket rather than leaving a silent gap for a reviewer to wonder about.

The permissions boundary, PermissionsBoundary, deployed as an iam.ManagedPolicy named lattice-lab-permissions-boundary, is the part of this stack worth being precise about, because the term gets used loosely. A permissions boundary is not an allow list and it is not additive with a role's identity policy. It is a ceiling. When a boundary is attached to a role, that role's effective permissions are the intersection of what its identity policy allows and what the boundary allows, and an explicit Deny anywhere in either one wins outright regardless of what the identity policy says. Attaching a broad managed policy to a role bounded this way does not actually widen what the role can do past the boundary's own ceiling. That is exactly the shape of this policy: an AllowProjectOperations statement with a long, curated list of what this project's roles legitimately need, ec2:Describe*, ssm:*, ssmmessages:*, ec2messages:*, logs:*, ecs:*, vpc-lattice:*, scoped DynamoDB item actions, scoped S3 object actions, and more, sits alongside an AllowScopedPassRoleToSageMaker statement that permits iam:PassRole only when the condition key iam:PassedToService equals sagemaker.amazonaws.com, and an AllowProjectKmsUsage statement that scopes kms:Decrypt, kms:DescribeKey, kms:GenerateDataKey*, kms:Encrypt, and kms:ReEncrypt* to exactly the five CMK ARNs built earlier in the stack, deliberately leaving out key management actions. On top of all of that sits DenyPrivilegeEscalation, an explicit Deny on iam:CreateUser, iam:CreateRole, iam:CreatePolicy, iam:CreatePolicyVersion, iam:AttachUserPolicy, iam:AttachRolePolicy, iam:AttachGroupPolicy, iam:PutUserPolicy, iam:PutRolePolicy, iam:PutGroupPolicy, iam:UpdateAssumeRolePolicy, iam:PassRole, and the four actions that would let a role tamper with permissions boundaries themselves, iam:DeleteRolePermissionsBoundary, iam:DeleteUserPermissionsBoundary, iam:PutRolePermissionsBoundary, and iam:PutUserPermissionsBoundary, with a StringNotEquals condition on iam:PassedToService carving out the sagemaker.amazonaws.com case so the sagemaker_stack.py Lambdas can still legitimately pass SageMakerExecutionRole into CreateTrainingJob and similar calls. A second Deny, DenyAccountAndOrgActions, blocks organizations:*, account:*, kms:ScheduleKeyDeletion, and kms:DisableKey outright. No identity policy attached to a bounded role, however permissive, can talk its way past those two Deny statements, and that is precisely the property that makes a permissions boundary useful as a hard ceiling rather than just another policy to audit.

The boundary only protects roles it is actually attached to, so the stack also produces SharedInstanceRole, named lattice-lab-shared-instance-role, trusted by ec2.amazonaws.com, carrying the AWS-managed AmazonSSMManagedInstanceCore policy, and built with permissions_boundary set to self.permissions_boundary from the start, plus a matching SharedInstanceProfile wrapping it. This is the plain, SSM-managed identity any EC2 instance in the project can use when it does not need a bespoke role of its own. The bespoke roles that already existed elsewhere, firewall_role, libreswan_role, and the others with their own trust and least-privilege reasoning documented at each call site, were refactored in the same pass to also take permissions_boundary=security.permissions_boundary, so the boundary's coverage extends to every role this project's own code authors, without collapsing their distinct identities into one shared role. I was explicit in the module docstring about the scope decision behind that: I applied the boundary through per-role permissions_boundary props on the roles this project's code creates, not as a blanket iam.PermissionsBoundary.of(app) Aspect over the whole App or Stage, because an Aspect would also retroactively catch every IAM role CDK generates internally for its own plumbing, BucketDeployment's role, AwsCustomResource providers, log-retention custom resources, including things like lattice_stack.py's SelfSignedCertImport and LatticeManagedPrefixListLookup, whose exact runtime IAM needs are not enumerated anywhere in this project's code and are not verifiable from cdk synth alone. A boundary that turned out too narrow for one of those would only ever surface as an AccessDenied deep into a real deploy, so I scoped the boundary to get real, verifiable coverage on every role I actually designed rather than gambling an already-working deployment on an unverified blanket change.

The last piece is IAM Access Analyzer, an accessanalyzer.CfnAnalyzer named lattice-lab-account-analyzer with type set to ACCOUNT. It runs at the account level and continuously evaluates resource-based policies, on the S3 buckets, the KMS keys, and anything else in the account with a resource policy, for any statement that grants access to a principal outside the account or its AWS Organization. It is a small piece of the stack on paper, a single CfnAnalyzer construct with two arguments, but it is the backstop that catches the failure mode none of the other controls in this stack are built to catch: a resource policy that, whether by a typo in a principal ARN or a wildcard added under deadline pressure, quietly opens something up to the internet or to an unrelated account. Everything else in SecurityStack, the five CMKs, the boundary, the shared role, is about constraining what principals inside this account can do. Access Analyzer is the one control watching for the door being left open from outside it, and putting it in the stack that deploys first and exports everything else as props meant that watch started running before a single other resource in the project existed.
