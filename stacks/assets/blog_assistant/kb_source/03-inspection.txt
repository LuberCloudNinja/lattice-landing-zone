Section: The Building Every Flight Passes Through
Topic: The Checkpoint

Plain English explanation:

Inside the inspection zone sits the actual checkpoint, and it is built to never be a single point of failure. Multiple screening lanes run in parallel across two separate wings of the building, so if one wing has a problem, the other keeps working without anyone at the gate even noticing. A dispatcher at the front door decides which lane each flight goes to, and if a lane goes down entirely, the dispatcher stops sending traffic there and reroutes everyone to a working lane automatically.

There is one detail that took real thought to get right. The inspectors staffing that checkpoint sometimes need to leave the building themselves, to pick up new rulebooks or restock supplies. If they used the same passenger checkpoint to do that, the inspection process would end up inspecting itself, which is both wasteful and, in a few edge cases, actually breaks things. So the inspectors have their own staff only exit, completely separate from the passenger flow, that never touches the checkpoint at all.

Technical explanation: The Inspection Layer

InspectionStack builds a Gateway Load Balancer named Gwlb (type gateway) that fronts a target group called FirewallTargetGroup, and the whole thing speaks GENEVE on port 6081, target_type instance. Health checking runs over TCP against port 8080, which is gwlbtun's confirmed health check port (GWLBTUN_HEALTHCHECK_PORT in the code, and it has to match the same constant baked into install-gwlbtun.sh on the box). Checks run every 10 seconds, and it takes 3 consecutive passes or failures (healthy_threshold_count and unhealthy_threshold_count, both set to 3) to flip an appliance's state. The target group also carries two explicit attributes, target_failover.on_deregistration and target_failover.on_unhealthy, both set to rebalance instead of AWS's default no_rebalance. That choice only matters because there are two appliances per AZ: rebalance means in-flight flows get moved onto the surviving healthy target immediately, instead of being black-holed until the Auto Scaling Group finishes replacing the dead instance.

The firewall fleet itself is deliberately not one shared multi-AZ ASG. It's one FirewallAsg per Availability Zone, each pinned to min_capacity, max_capacity, and desired_capacity all equal to config.FIREWALL_APPLIANCES_PER_AZ, which is 2. The reasoning in the code is that a single multi-AZ ASG's built-in AZ rebalancing can transiently drift away from a strict per-AZ count during scaling events, and this design wants that count to hold exactly. Each ASG runs the same FirewallLaunchTemplate: Ubuntu 24.04 LTS pulled from Canonical's own SSM parameter path, IMDSv2 required, and a 20 GB gp3 root volume (not the 8 GB default) encrypted with security.ebs_key, sized up because building gwlbtun from source with Boost and CMake, plus pulling in Suricata's ET Open ruleset, needs real disk. Since GWLB target groups aren't one of the L2 AutoScalingGroup's attach_to_target_group helpers (those only cover ALB and NLB), the code drops to the L1 escape hatch, cfn_asg.target_group_arns, to wire each ASG straight into FirewallTargetGroup.

Boot is where the nftables and Suricata story actually plays out. User data installs unzip, awscli, and nftables via apt-get, pulls down a software asset bundle from S3 (the install scripts, generate_nft.py, and pl-sync.sh, all zipped together because the bundle runs around 85KB, well past the 16KB user-data limit), and then sources install-gwlbtun.sh and install-suricata.sh from inside bash wrapper functions rather than executing them directly. The reason is that both scripts use return statements to abort early on a failed step, and return only behaves correctly inside a function or a sourced script, not a subprocess. After nftables and pl-sync's systemd units are in place, the boot script runs pl-sync.sh synchronously once before ever enabling pl-sync.timer, specifically so the ASG's health check, which has a 10 minute grace period to accommodate this whole install, never marks an instance healthy while it's still running with zero policy loaded. FirewallSg only opens two things, both scoped to the inspection VPC's own CIDR block: GENEVE on UDP 6081 from the GWLB, and TCP 8080 for the gwlbtun health check. The real enforcement boundary is the nftables policy itself, not this security group.

Getting traffic into the firewall fleet requires two layers of GWLB Endpoints plus one route table trick that's easy to miss. GwlbEndpointService fronts the Gwlb with acceptance_required set to False, since this is a single-account lab and there's no cross-account PrivateLink handshake to gate. Because CfnVPCEndpointService doesn't expose a ServiceName attribute, the code builds the service name itself from the documented com.amazonaws.vpce.<region>.<service-id> format using attr_service_id. One GwlbEndpoint gets created per Availability Zone inside inspection-vpc's GwlbEndpoint subnets, and each TgwAttach subnet gets a 0.0.0.0/0 route pointed at the endpoint in the same AZ, matched explicitly by availability_zone rather than by list position. A second, separate set of endpoints, AppVpcGwlbEndpoint per subnet, gets created inside app-vpc itself, because a VPC endpoint can only serve as a route target for route tables that live in its own VPC. These app-vpc endpoints sit in the same public subnets as the NAT Gateway, since a GWLB Endpoint and a NAT Gateway are different resource types and happily coexist in one subnet.

The redirect trick is the ingress route table, AppVpcIngressRouteTable, associated with app-vpc's internet gateway itself through CfnGatewayRouteTableAssociation, which is what makes it an edge-association (ingress) route table rather than an ordinary subnet route table. Without this piece, inbound reply packets for outbound-initiated sessions would land at the IGW and route straight to the NAT Gateway using the normal per-subnet route table, completely bypassing inspection on the return leg. Each route in that table, named IngressRedirect plus the subnet's construct id, matches the app-vpc public subnet's own CIDR block (that subnet only ever holds the NAT Gateway) and sends it to the matching app-vpc-local GWLB endpoint instead, since CfnNatGateway doesn't expose its private IP as a CDK attribute and a subnet CIDR match covers the same ground without an extra runtime lookup.

Symmetry across all of this comes down to two things working together, and the module docstring is explicit that an earlier draft got this wrong. There is no target-group-level Appliance Mode toggle on a GWLB target group, that attribute simply doesn't exist. The actual Appliance Mode switch lives over in NetworkStack, on the inspection VPC's Transit Gateway attachment, set to appliance_mode_support enable. FirewallTargetGroup's job here is just to stay out of the way: it's left at its default 5-tuple stickiness, meaning no stickiness.* attributes are set on it at all, because 2-tuple or 3-tuple stickiness is documented as flatly incompatible with TGW Appliance Mode rather than an alternate way to express the same idea. Put together, the TGW attachment's Appliance Mode setting is what pins a given flow to one appliance for both directions, and the target group's default stickiness is what makes sure nothing at the GWLB layer second-guesses that decision by rehashing the flow onto a different one of the two appliances per AZ.
