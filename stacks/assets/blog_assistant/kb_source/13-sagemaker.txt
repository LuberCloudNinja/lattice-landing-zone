Section: The Seismograph Under the Runway
Topic: Listening for Trouble

Plain English explanation:

Sensors under the runway log every vibration, day after day, building up a picture of what normal actually looks like. Once a week that history trains a fresh model of normal. Every six hours, new readings get compared against that model in bulk, and anything that does not fit gets flagged, not because a person wrote a rule for it, but because it deviates from the pattern the model learned on its own.

Findings get handed straight to the assistant in the tower, who can factor them into whatever question gets asked next. And because the actual training and scoring jobs are not the kind of thing that can just be torn down cleanly like an ordinary resource, a dedicated cleanup routine sweeps up everything those jobs created whenever this whole layer gets shut off, so nothing keeps quietly running (and billing) after the fact.

Technical explanation: The SageMaker Anomaly Pipeline

The starting fact that shapes this entire stack is that AWS::SageMaker::TrainingJob and AWS::SageMaker::TransformJob simply do not exist as CloudFormation resource types. A training job and a transform job are one shot API calls, not declarative infrastructure, so there is nothing for CDK to own in the usual sense. Everything downstream of that fact in sagemaker_stack.py is boto3 driven from inside Lambda functions rather than synthesized as CfnResources, and the stack's docstring is explicit about why: there is no model artifact to point CreateModel at until an actual training run has produced one. So the pipeline is six pieces stitched together with EventBridge rules and Lambda, not a static template.

Data starts with an ec2.FlowLog named AppVpcFlowLog attached directly to app_vpc, writing into the raw/ prefix of a single bucket called SageMakerDataBucket. That bucket is deliberately not split into four or five buckets, it is one KMS encrypted, versioned, block-all-public-access bucket partitioned by prefix (raw/, processed/, training-output/, transform-output/, findings/, async-output/), with a lifecycle rule that expires anything under raw/ after 30 days so the flow log firehose does not grow unbounded. A daily Lambda called flow_log_preprocessor (function name rcf-flowlog-flow-log-preprocessor, five minute timeout at 300 seconds) reads that raw prefix and writes numeric feature CSVs into processed/. Once a week, on a seven day EventBridge rate schedule, rcf_trainer calls CreateTrainingJob against that processed data using the built in Random Cut Forest algorithm container. The image URI is built at synth time from the constant RCF_TRAINING_IMAGE_ACCOUNT, 382416733822, which the code comments note is AWS's documented built in algorithm registry account, templated per region as {account}.dkr.ecr.{region}.amazonaws.com/randomcutforest:latest rather than hardcoded to one region.

Training completion fires an EventBridge rule called TrainingJobCompletionRule, matching source aws.sagemaker, detail type SageMaker Training Job State Change, and a TrainingJobName prefix of rcf-flowlog-training-, which invokes rcf_model_promoter. On the very first successful run this Lambda creates the SageMaker model, endpoint config, and the endpoint itself, named rcf-flowlog-endpoint. On every run after that it updates the existing endpoint in place instead, then deletes the previous generation's model and endpoint config so old generations do not pile up as orphaned resources. The endpoint type is Async Inference, and the stack's opening comment is unusually direct about why that choice was made over Serverless Inference: Serverless Inference endpoints have no vpc_config option at all, which would mean scoring live VPC Flow Log data from an endpoint sitting entirely outside app-vpc's network boundary, a real break in the project's zero trust posture. Async Inference supports VpcConfig and supports scaling its instance count to zero through Application Auto Scaling when idle, which the promoter registers on first creation via RegisterScalableTarget and PutScalingPolicy with MAX_CAPACITY set to 1, meaning the endpoint scales between zero and one instance rather than sitting warm around the clock.

Every six hours, on an events.Schedule.rate(Duration.hours(6)) rule, rcf_batch_scorer calls CreateTransformJob against the same processed/ data using whatever model generation is currently promoted to the endpoint. This is a deliberately separate, systematic bulk sweep, distinct from any on demand invocation path against the live endpoint. When that transform job completes, a second rule, TransformJobCompletionRule, matches detail type SageMaker Transform Job State Change with a TransformJobName prefix of rcf-batch-score- and hands off to rcf_findings_processor. That Lambda reads the RCF anomaly scores, keeps anything at or above an ANOMALY_SCORE_THRESHOLD of 3.0, and writes qualifying findings into a DynamoDB table named sagemaker-anomaly-findings (partition key finding_type as a string, sort key detected_at as a number, on demand billing, customer managed KMS encryption via security.secrets_key, point in time recovery turned on) as well as into S3 and out to an SNS topic also named sagemaker-anomaly-findings, which carries an email subscription to config.REMEDIATION_EMAIL. That same DynamoDB table is what agentic_ai_stack.py's detect_anomalies MCP tool reads from, which is the actual point of the whole pipeline: turning raw flow log noise into something an agent can query.

Because the endpoint, its model, its endpoint config, and its Application Auto Scaling target are all created imperatively at Lambda runtime rather than declared at synth time, cdk destroy has nothing native to clean up when the stack is torn down, which is exactly the gap TeardownCleanup exists to close. It is wired in as a Custom Resource, a cr.Provider wrapping the cleanup Lambda as its on_event_handler, so it fires specifically on stack deletion. Its role is granted ListEndpoints, DeleteEndpoint, ListEndpointConfigs, DeleteEndpointConfig, ListModels, DeleteModel, and DeregisterScalableTarget, all scoped to resource '*' because there is no ARN to narrow to in advance, and the real safety net is the NAME_PREFIX convention, rcf-flowlog-, that every resource this pipeline creates at runtime follows, so the sweep only touches what this pipeline actually owns. The teardown Lambda itself runs with a 120 second timeout and, notably, is never given an explicit function_name the way the five orchestrator Lambdas are, since it does not need to be discoverable by the NAME_PREFIX convention, it is the one doing the discovering.

The networking around all of this stays consistent with the rest of the project's zero trust stance. Two interface VPC endpoints, SAGEMAKER_API for control plane calls like CreateTrainingJob and SAGEMAKER_RUNTIME for InvokeEndpointAsync on the data plane, sit in the Private subnet group behind a security group that only allows inbound tcp 443 from the app-vpc's own CIDR block. They are created sequentially rather than in parallel, with an explicit node dependency between them, to sidestep the same Route53 private hosted zone provisioning race the project had already run into with the paired Bedrock endpoints in agentic_ai_stack.py. The orchestrator Lambdas' own security group, SageMakerLambdaSg, is outbound only with no ingress rules at all, which is all five of them need since nothing calls into a Lambda ENI directly. The stack closes with four cdk-nag suppressions on its own IAM choices (IAM4 for the AWS managed VPC access and basic execution policies, IAM5 for the wildcard resource on sagemaker and application-autoscaling actions, justified by the same NAME_PREFIX reasoning as the teardown sweep, L1 for Python 3.13 being the current runtime, and S1 for the data bucket's access logs pointing at a logs bucket that deliberately does not log to itself), which is a small but telling sign that the wildcards here were a considered tradeoff rather than an oversight.
