Section: The Wing Still on the Blueprint
Topic: Planned, Not Yet Built

Plain English explanation:

Not every part of an airport gets built in the first phase, and pretending otherwise would be dishonest. There is a wing on the blueprint that has not been built yet, meant eventually to house a message broker that other parts of the airport will eventually rely on for passing information around in real time. It is marked clearly as future work, feature flagged off, sitting in the plans on purpose rather than quietly missing.

Including a deliberately unfinished piece in a portfolio project is its own kind of honesty. It shows how a real plan gets staged over time, not just what a finished result looks like at the end.

Technical explanation: The Planned Kafka Layer

stacks/kafka_stack.py is the one file in this project I am not going to pretend is finished. The class is called KafkaStack, it subclasses the standard aws_cdk Stack, and its own docstring says exactly what it is: "real KRaft Kafka on EC2, deployed last, feature-flagged off first." It points directly at SPEC.md Section 6, which laid out the same instruction before a line of stack code existed. Whether this stack even gets instantiated is controlled entirely from the outside, by config.ENABLE_KAFKA in stage.py. The class itself has no internal flag check, and that is called out explicitly in the module docstring, because the gating belongs at the composition layer where all the stacks get wired together, not scattered inside each individual construct.

Right now the constructor does almost nothing. It calls super().__init__, and it tags itself with Tags.of(self).add("Layer", config.Layer.KAFKA), which is the same tagging convention every other stack in this project follows so that cost and resource ownership can be traced back to a layer at a glance. After that there is a block of TODO comments and nothing else. No EC2 instance, no security group, no VPC lookup, no CfnOutput. It is, in the most literal sense, a skeleton: a stack class that exists, is wired into the app, and today produces an empty CloudFormation template.

What it is meant to become is spelled out in those TODO comments, and I want to be precise about it rather than paraphrase loosely, because the whole point of this section is honesty about what is built versus what is planned. The plan is a self-managed Kafka broker running in KRaft mode, meaning no ZooKeeper, on an EC2 instance placed inside onprem-vpc. User data on that instance would install Kafka, format its storage with kafka-storage.sh, and start the broker listening on port 9092, with the advertised listener set to the instance's own private IP so that clients on the other side of the mesh resolve back to something actually reachable instead of a loopback address. Once that broker is running, the plan calls for repointing LatticeStack's L4e resource configuration at it, which means swapping out the placeholder ncat listener that NetworkStack currently exposes and replacing it with the real broker endpoint. The last item in the TODO list is a producer and consumer test that has to be reachable from the app-vpc consumer through the Lattice mesh itself, which is really the whole thesis of the project: prove that a service in one VPC can talk to a workload in a completely separate VPC entirely through Lattice's service network, no VPC peering, no transit gateway route table entries.

I included this stack unfinished on purpose, and I think that is worth saying directly rather than letting a reviewer wonder why an empty class is sitting in the repo. Deploying self-managed Kafka on EC2 is a meaningfully bigger and riskier step than anything else in this project so far, it means an always-on instance, storage that has to be provisioned and formatted correctly the first time, and a broker configuration that has real consequences if the advertised listener is wrong. Rather than fake that work with a stack that looks complete but was never actually exercised against a real broker, I staged it: the class exists, the tagging convention is already correct, the deploy order is already decided (last, after everything else is stable), and the feature flag that will turn it on lives in exactly the same place as every other environment toggle in config.py. Anyone reading this code six months from now, including me, can see precisely what is left to do without having to reconstruct intent from a commit message.

The honest reason I have not built it out yet also matters, and it is not laziness. This project has been running against a tight vCPU quota, and adding an always-on EC2 broker competes directly with instance capacity I do not currently have headroom for. Rather than force it in and destabilize a working Lattice mesh, I left KafkaStack exactly where SPEC.md Section 6 says it should sit until that constraint clears: staged, flagged off, and ready to be finished in the order the plan already specifies. That is the part I actually want a hiring panel to notice, not that every stack in this repository is done, but that the ones that are not done are marked as such deliberately, sequenced correctly, and gated behind a flag instead of being quietly hidden or, worse, half wired into stacks that depend on them.
