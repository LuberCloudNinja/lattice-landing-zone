Section: The Guide Who Only Answers From the Building Plans
Topic: An Assistant Who Knows the Building

Plain English explanation:

Imagine a guide stationed at the entrance who has actually read every plan, every manual, every record this airport has ever produced, and will answer any question about the place using only what is written in those documents. Ask something outside the documents and the guide says so honestly instead of making something up to sound helpful. Ask a follow up question and the guide remembers what was asked a moment ago, because the conversation gets written down as it happens, not just held in the guide's head where it disappears the moment the guide walks away.

That is the assistant available on this very blog post. It answers questions about this project using the project's own writing, both the plain language sections and the technical sections, as its only source of truth. It keeps a short written record of each conversation so a follow up question makes sense in context, and that record gets cleared out automatically after thirty days rather than kept forever.

Technical explanation: Retrieval Augmented Generation With Explicit Memory

The assistant embedded on this blog is built as its own standalone stack, blog_assistant_stack.py, deployed unconditionally alongside blog_analytics_stack.py rather than gated behind the ENABLE_AI flag that controls agentic_ai_stack.py. The reasoning is simple. The blog itself is always on, so the thing answering questions about the blog needs to always be on too, with no feature flag standing between a visitor and a working chat box.

Under the hood it mirrors agentic_ai_stack.py's semantic memory tier closely, because that tier already solved the hard problems once. An S3 Vectors vector bucket and index hold 1024 dimensional embeddings produced by Amazon Titan Embed Text v2, cosine distance, exactly the same configuration already proven in this project. A Bedrock Knowledge Base sits on top of that index, backed by an IAM role that needed the same two fixes the earlier build already discovered the hard way. S3 Vectors runs its own asynchronous indexing under its own service principal, indexing.s3vectors.amazonaws.com, which needs an explicit KMS grant separate from any general purpose grant on the bucket's encryption key, or indexing fails with an access denied error that has nothing obviously to do with the actual missing permission. And a plain role_arn reference on the Knowledge Base resource does not create a CloudFormation dependency on the separate IAM Policy resource that grants s3vectors:QueryVectors, so without an explicit iam.Policy construct held onto and referenced with add_dependency, the Knowledge Base can start creating before its own role actually has permission to query the index it needs, and fails with a permissions error that looks like a race condition because it is one.

The content the knowledge base actually knows about is this project's own blog writing. Thirteen plain text files, one per section, each containing both the plain language explanation and the technical explanation for that layer, get uploaded to a private source bucket through a BucketDeployment at deploy time, and the Bedrock data source ingests them into the vector index from there. Nothing gets ingested per request. The knowledge base is built once, when the stack deploys, from whatever the blog's own content looked like at that moment.

A single Lambda, blog-assistant-ask, handles every request end to end. It calls bedrock-agent-runtime Retrieve against the knowledge base to pull back the five most relevant passages for whatever the visitor just asked. It reads the conversation history for that visitor's conversation id from a dedicated S3 memory bucket, a plain JSON array of prior turns, capped at a fixed number of turns so the history cannot grow without bound. It builds a message list combining that history with the new question and the retrieved passages, and sends the whole thing to Anthropic's Claude model, config.BEDROCK_MODEL_ID, through Bedrock's Converse API, which is the modern, model family agnostic way to have a multi turn conversation with a Bedrock hosted model rather than hand building a model specific request body. Once the model responds, the handler appends both the question and the answer to the history and writes the updated array back to the same S3 object, then returns the answer to the caller.

Getting a request there at all follows the same routing pattern blog_analytics_stack.py already established. CloudFront gets a new behavior, /assistant/star, added onto ThreeTierStack's existing distribution from inside this stack rather than inside threetier_stack.py itself, the same cross stack construct mutation pattern auto_heal_stack.py uses on observability_stack.py's dashboard. One detail worth being explicit about because it caused a real bug during this exact build: CloudFront forwards the full request path to the origin unchanged. A /assistant/star cache behavior does not strip that prefix before forwarding, so the API Gateway route registered in this stack has to be the full path the browser actually calls, /assistant/ask, not just /ask. Getting that wrong produces a working CloudFront distribution and a working API Gateway that still return a 404 to every real request, because the two sides are listening on different paths.

Memory in this design is deliberately a plain S3 object rather than any framework provided session cache. That choice is consistent with how the rest of this project treats state. It can be opened, read, and deleted like any other file, not hidden behind an abstraction that only the framework itself can inspect.
