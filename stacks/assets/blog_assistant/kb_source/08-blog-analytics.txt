Section: The Visitor Ledger That Forgets on Purpose
Topic: Reading The Ledger

Plain English explanation:

A busy building keeps a visitor ledger, a simple record of who came through, when, and whether they made it all the way to the exhibit at the end of the hall. This project keeps one too, for this very blog post. It notes when someone arrives, whether they read to the end, whether they followed the link to the source archive on the way out, and roughly how long they stayed.

The ledger is deliberately built to forget the fine grained detail after a while. Individual entries get shredded automatically after six months. What survives permanently is just the count, how many visitors, how many finished reading, how many followed the link, not who any specific one of them was. That is a real design choice, not an accident, and it is one worth being upfront about.

Technical explanation: Blog Read Analytics

The blog read analytics piece lives in its own stack, BlogAnalyticsStack, and it deploys unconditionally alongside the rest of the project the same way governance_stack.py does, because an API Gateway HTTP API, one low traffic Lambda function, and an on demand DynamoDB table add up to lab scale cents, not the kind of spend that needs a config.py feature flag to gate. Rather than standing up a second CloudFront distribution just to serve a beacon endpoint, it reaches into ThreeTierStack's existing distribution and adds a new cache behavior for the path pattern /analytics/*, the same cross stack construct mutation pattern auto_heal_stack.py already uses when it extends observability_stack.py's dashboard from a separate file. That behavior points at an origins.HttpOrigin built from the HTTP API's own domain, pulled out of the api_endpoint token with cdk.Fn.select(2, cdk.Fn.split("/", self.http_api.api_endpoint)), and it runs with OriginProtocolPolicy.HTTPS_ONLY, ViewerProtocolPolicy.REDIRECT_TO_HTTPS, CachePolicy.CACHING_DISABLED, and OriginRequestPolicy.ALL_VIEWER_EXCEPT_HOST_HEADER. That combination means beacon calls are never cached, always travel encrypted, and arrive same origin from the browser's point of view, which is also why the API's own CORS configuration barely matters in production even though it is left wide open.

On the client side, a component called AnalyticsBeacon.tsx posts JSON to that /analytics path, and the request lands on a single HttpApi named blog-analytics-api with exactly one route, POST /events, wired through an integration called IngestIntegration. The Lambda behind it, function name blog-analytics-ingest with the CDK construct id BlogAnalyticsIngest, runs Python 3.13 on the ARM_64 architecture with 256 MB of memory and a 10 second timeout, generous headroom for a function that does one DynamoDB put and one CloudWatch PutMetricData call per invocation and nothing else. Its entry point, handler.handler in handler.py, only accepts four event types, page_view, read_complete, github_click, and session_end, checked against an ALLOWED_EVENT_TYPES set, and anything outside that set gets a 400 response before it ever touches the table. A successful write returns a bare 204 with CORS headers attached, matching the fire and forget intent of a beacon, there is nothing for the client to read back. The stack also exposes the endpoint and the table name as CfnOutputs, BlogAnalyticsApiEndpoint and BlogAnalyticsTableName, so both are easy to find after a deploy without digging through the console.

The table itself, construct id BlogAnalyticsEvents with the physical name blog-analytics-events, is a TableV2 keyed on sessionId as the partition key and eventTimestamp, a millisecond epoch number, as the sort key, so every event a single browser session generates lands as its own item under that session's partition. A global secondary index named EventTypeByTime reindexes the same data by eventType and eventTimestamp, so a dashboard query or any future ad hoc lookup can pull every page_view or session_end row across all sessions without a full table scan. Billing is on demand, encryption uses the customer managed key from security.buckets_key rather than an AWS owned key, point in time recovery is explicitly turned on, and the removal policy is DESTROY, consistent with every other lab scale resource in this project that the owner is comfortable losing on a stack teardown.

The interesting design decision is what gets to live forever and what does not. Every item the handler writes carries an expiresAt attribute set to the current epoch second plus TTL_DAYS times 86400, and TTL_DAYS is 180, so every raw event, including the fields that actually matter for privacy, ages out of DynamoDB on its own after about six months with no cleanup job required. The source IP comes from the first entry in the X-Forwarded-For header, which CloudFront itself overwrites at the edge so a client cannot spoof it, and the country comes straight off the CloudFront-Viewer-Country header CloudFront injects on every request. Neither of those per visitor fields, sourceIp especially, is ever sent to CloudWatch. What the handler publishes under the LatticeLab/BlogAnalytics namespace is strictly aggregate: a count of 1 against PageViews, ReadCompletions, GithubClicks, or SessionEnds depending on event type, dimensioned only by Country, plus, for session_end events where timeOnPageMs is greater than zero, a TimeOnPageSeconds value and a MaxScrollPercent value with no dimension at all. CloudWatch metrics do not carry a TTL the way the DynamoDB items do, so the dashboard's reads and drop off panel and its engagement depth panel keep their full history long after the raw row behind any given data point has expired and disappeared. That split, raw and identifying data expires, aggregate and anonymous data persists, is exactly what the handler.py docstring argues for directly: IP addresses are personal data under GDPR and CCPA, so they are confined to the TTL'd raw events table and deliberately kept out of the permanent record.

The ingest role, BlogAnalyticsIngestRole, is assumed only by lambda.amazonaws.com, bound by security.permissions_boundary like every other execution role in this project, and otherwise kept narrow apart from one necessary wildcard. It gets table.grant_write_data() for puts, security.buckets_key.grant_encrypt_decrypt() so it can write through the customer managed key, the AWS managed service-role/AWSLambdaBasicExecutionRole policy for CloudWatch Logs, and a hand written statement allowing cloudwatch:PutMetricData against resources set to ["*"], because metric namespaces are not ARN scoped resources in IAM and there is no narrower way to grant that particular permission, the same reasoning governance_stack.py already used for its own GovernanceMetricsRole. The stack carries six matching cdk-nag suppressions: AwsSolutions-IAM4 for the managed logs policy, IAM5 for the PutMetricData wildcard, L1 because Python 3.13 is simply the newest managed Lambda runtime available at build time, APIG1 because access logging on a single route ingest API would just duplicate what the Lambda's own log group, BlogAnalyticsIngestLogGroup, one month retention, encrypted with security.logs_key, already captures, APIG4 because the endpoint is intentionally open write only telemetry with no per visitor identity to authorize against, and DDB3 because point in time recovery is already enabled on the table. Each suppression reads less like a shortcut and more like a paper trail, written into the code itself, explaining exactly why a relaxed rule is acceptable in this specific context.
