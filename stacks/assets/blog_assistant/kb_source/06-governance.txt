Section: The Security Operations Center
Topic: Watching Everything, Fixing the Small Things

Plain English explanation:

Every well run airport has a room full of screens that nobody outside security ever sees. Cameras record everything, not so someone can watch live all day, but so that if something goes wrong at two in the morning, there is a complete record of exactly what happened. A compliance inspector walks the terminals on a fixed schedule, checking that fire doors are not propped open and that badges have not been left in an unlocked drawer. A threat desk watches for patterns that look like the start of trouble, not just individual rule breaks.

When something small and well understood goes wrong, a door left unlocked by mistake, an automatic response team fixes that one specific door immediately rather than paging the airport director to handle it personally. That team never runs a broad sweep through the whole property. It only ever touches the one thing the alert actually named.

Technical explanation: Governance, Drift Remediation, and Auto Heal

The landing zone runs three independent control loops instead of one unified one, and that separation is a deliberate design choice, not an accident of how the code grew. GovernanceStack is a pure detection plane: CloudTrail, AWS Config, Security Hub, and GuardDuty, none of which have the ability to change anything, they only observe and score. DriftRemediationStack is a security control aimed at a specific threat model, a human making a manual change outside the CI/CD pipeline, and it is the one place in the whole project where a Lambda actually holds delete permissions triggered off a live API call. AutoHealStack is an operations control aimed at a completely different problem, three named, well understood infrastructure failure modes that have nothing to do with who made a change and everything to do with keeping already approved infrastructure running. Collapsing these into a single mega-remediator would mean one execution role and one code path carrying both the logic that decides whether to delete a stranger's EC2 instance and the logic that reboots a known host on a failed status check, two very different trust boundaries and blast radii that are much easier to reason about, test, and suppress cdk-nag findings against when they stay apart.

GovernanceStack wires up CloudTrail as a multi-region trail named lattice-lab-trail, with include_global_service_events, enable_file_validation, and management_events set to ReadWriteType.ALL, delivering to both a CMK-encrypted, versioned S3 bucket and a CloudWatch log group (CloudTrailLogGroup, one month retention) that is what EventBridge actually reads in practice. Getting that CloudTrail bucket working required an extra explicit KMS grant, security.buckets_key.grant_encrypt_decrypt(iam.ServicePrincipal("cloudtrail.amazonaws.com")), because the Trail L2 construct wires the bucket policy automatically but not the CMK's own resource policy, which surfaced as a live deploy failure before being caught. AWS Config runs a single recorder named lattice-lab-recorder with all_supported and include_global_resource_types both true, paired with a delivery channel named lattice-lab-delivery-channel, and the stack deliberately declares no CDK dependency between the two because both directions were tried and both failed live (the recorder deadlocks waiting on a channel that never starts, or the channel throws NoAvailableConfigurationRecorderException), so each resource's own PUT call is left to succeed on its own per the documented fix in aws/aws-cdk#3492. On top of the recorder sit eight managed Config rules: required tags (keyed on Project and Layer), S3 bucket versioning, S3 server side encryption, EBS encrypted volumes, CloudTrail enabled, VPC flow logs enabled, restricted SSH ingress, and no IAM policy statements with admin access. Security Hub is enabled with enable_default_standards set to false so the stack can pin exactly two standards on purpose, AWS Foundational Security Best Practices v1.0.0 and CIS AWS Foundations Benchmark v3.0.0 (the code notes that v1.2.0 no longer exists as a subscribable standard, confirmed against the live Security Hub API), and GuardDuty runs as a single CfnDetector enabled unconditionally because its cost at lab scale is negligible. Because none of Config, Security Hub, or GuardDuty publish a native CloudWatch findings-count metric, a small Lambda named governance-metrics-publisher polls all three every 15 minutes and writes into a custom namespace, LatticeLab/Governance, purely so the observability dashboard has something to graph.

DriftRemediationStack answers a narrower and more dangerous question: what happens within seconds of someone making a change by hand instead of through the pipeline. An EventBridge rule, ManualMutationRule, watches CloudTrail's AWS API Call via CloudTrail management events for eventName prefixes Create, Run, Put, Modify, Delete, Attach, and Authorize, filtered to exclude anything whose userIdentity.arn starts with the CDK bootstrap's shared execution role, cdk-hnb659fds-cfn-exec-role-{account}-{region}, which every pipeline deploy and every manual cdk deploy under the deloitte-admin profile authenticates through. Because a Lambda with delete permissions triggered off a raw API call is inherently risky, the design stacks four independent gates on top of that first EventBridge filter: the handler re-derives the same execution role exclusion itself, it does a live IAM tag lookup for BreakGlass=true on the calling principal, it does a live tag lookup for ManagedBy=cdk on the resource the event actually touched, it only recognizes a small explicit allow list of eventSource and eventName pairs with no generic best effort delete path, and config.DRY_RUN (false by default) can flip the whole thing to alert only. The Lambda itself, drift-remediator, runs inside app_vpc's Private subnets behind a security group named RemediatorSg with outbound only egress, and its IAM role is split into two statements, ReadForGating (describe and list-tags calls across ec2, s3, iam, dynamodb, sns, lambda, and logs) and ScopedRemediation (an explicit, non-wildcard list of delete actions: ec2 TerminateInstances, DeleteSecurityGroup, DeleteVolume, s3 DeleteBucket, iam DeleteRole, dynamodb DeleteTable, sns DeleteTopic, lambda DeleteFunction, logs DeleteLogGroup). Every alert, whether the Lambda takes action or not, goes to a CMK-encrypted SNS topic named governance-alerts with an email subscription to config.REMEDIATION_EMAIL. The net effect the module docstring calls out directly is that this mechanism can only ever delete one specific, newly created, untagged resource made by a non-break-glass principal outside the pipeline, never a sweep, never anything pipeline-managed.

AutoHealStack is not a security control at all, it is a resilience loop for three named failure modes, each mapped to exactly one resource the stack already holds a reference to. The first is vpn-tunnel: a CloudWatch alarm named VpnTunnelDownAlarm watches the AWS/VPN TunnelState metric on network_stack's Site-to-Site VPN connection, threshold 1, comparison LESS_THAN_THRESHOLD, two evaluation periods, missing data treated as breaching, and on alarm it dispatches an SSM Run Command using the AWS-RunShellScript document against the Libreswan instance to restart ipsec and force IKE renegotiation. The second is lattice-target: LatticeTargetUnhealthyAlarm watches AWS/EC2 StatusCheckFailed on threetier_stack's Lattice INSTANCE-type target host, threshold 1, GREATER_THAN_OR_EQUAL_TO_THRESHOLD, two evaluation periods, missing data treated as not breaching, and remediation is a plain ec2:RebootInstances call scoped to that one instance ARN. The third, bedrock-throttle, only gets wired when agentic_ai is present (config.ENABLE_AI on): one alarm per persona on the orchestrator Lambda's error metric, threshold of 3 errors, one evaluation period, and it is intentionally alert only, since a Bedrock TPS quota problem needs a support ticket rather than an infrastructure action. All three alarms feed a Step Functions state machine named auto-heal that runs NotifyBefore (an SnsPublish task to drift_remediation.alerts_topic with subject auto-heal: remediation starting), then RemediateTask (a LambdaInvoke against a function named auto-heal-remediate that dispatches on a remediation_type field), then NotifyAfter (SnsPublish with subject auto-heal: remediation complete), with logging level set to ALL and X-Ray tracing enabled on the state machine. Every alarm also fires an SnsAction straight to the same governance-alerts topic independent of the Step Functions path, so a human gets the identical signal the automation is acting on rather than having to trust the automation silently.

Read side by side, the three loops map cleanly onto three different questions the landing zone needs answered, and none of them substitute for each other. Governance answers is the account compliant right now, on a recurring evaluation cycle, with zero mutate permissions anywhere in that stack. Drift remediation answers did someone just do something outside the pipeline, and it earns its delete permissions only after passing four separate, independently falsifiable gates because that is the one loop where the blast radius of a mistake is a human's infrastructure getting deleted. Auto heal answers is a known, named piece of infrastructure currently broken in one of three specific ways, and it never touches anything it doesn't already hold a direct construct reference to, whether that's network.libreswan.instance_id or threetier.lattice_instance_target_host.instance_id. Keeping them as three stacks also means three independently testable, independently disableable surfaces: DRY_RUN only affects drift remediation, the Config managed rules run on their own schedule regardless of whether the remediation Lambda is even deployed, and auto heal's alarms can be tuned or unwired per failure mode without touching the CloudTrail-driven security path at all. That separation is the whole point. A single combined Lambda watching both unauthorized human changes and known infrastructure failures would have to reason about two unrelated trust boundaries in one place, and the cdk-nag suppressions attached to each stack, each with its own written justification for IAM4, IAM5, and the Step Functions specific SF1 and SF2 findings, are the clearest evidence that each mechanism was scoped and audited on its own terms rather than inherited from a shared template.
